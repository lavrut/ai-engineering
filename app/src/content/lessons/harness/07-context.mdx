## Concept

The model remembers nothing between calls (lesson 2), so every request carries the whole conversation. Each turn of the loop adds two messages: the model's reply and one user message of tool results (lesson 4). The request grows on every pass, and you pay for all of it every time.

The hard limit is the <Term t="context window" />: the most tokens one request can hold, counting the system prompt, the tool schemas, every message and the reply. For `claude-opus-5-5` it is 1,000,000 tokens. A request over the window fails.

The harness sets its own, much lower limit: `CONTEXT_BUDGET`, 150,000 input tokens. It does not guess the size of the history. Every response carries <Term t="usage" />, and `usage.input_tokens` is the exact number of tokens the request just sent. After a tool turn, step 9 of the flow compares that number with the budget.

When the budget is exceeded, the harness performs <Term t="compaction" />. It asks the model to summarize the session so far, then starts a new conversation whose only message is that summary. The work carries on, and the next request is small again.

There is a rule behind this design: the harness never edits an earlier turn. Current Claude models reject a history that was changed after the fact; a reply, including its thinking blocks, is bound to the exact conversation that produced it. So the harness cannot shorten old tool results or drop the oldest turns. The history is append-only, and the only way to make it smaller is to start a fresh one.

The meter is simpler than the harness in two ways. It counts the turn it just added; the harness checks `input_tokens` from the request it just sent, which does not include the tool results it has just appended. And the meter compacts at once; the harness spends one extra model call writing the summary.

## The code

Section 7 is the context manager.

<CodeTabs section={7} goNote="compact takes the same steps and returns ([]anthropic.MessageParam, error), so a failed summary call reaches main as an error value. The summary request sets MaxTokens: 4000 and ToolChoice with OfNone. callModel only fills in maxTokens when the field is zero, so the 4000 stands. In runAgent the call is written messages, err = compact(...) with = and not :=, so the new list replaces the outer messages instead of a copy that would vanish at the end of the if." />

The check that calls it is in the agent loop (section 8), right after the tool results are appended:

```python
if response.usage.input_tokens > CONTEXT_BUDGET:
    messages = compact(messages, call)
```

It runs only on the `tool_use` path. On `end_turn` the session ends anyway, and the next task you type starts a new `messages` list in `run_agent`.

`compact` does four things:

- `emit("compact", messages=len(messages))` logs how many messages the old conversation had.
- `ask` is one more user message: "Summarize this session for a fresh start: the goal, what you did, files touched, and what is left to do."
- `call(messages + [ask], tool_choice={"type": "none"}, max_tokens=4_000)` sends the whole history plus the request. `messages + [ask]` builds a new list, so the old one is left as it was. `tool_choice` set to `none` tells the model to answer in text and call no tools, even though `call_model` still sends the tool schemas. `max_tokens=4_000` caps the summary. Both go through the `overrides` you saw in `call_model` in lesson 2. The request list ends with two user messages in a row: the tool results, then `ask`. The API combines consecutive turns from the same role into one, so the alternation rule from lessons 2 and 4 still holds.
- The return value is a new list with one user message: `"Summary of earlier work:\n"`, the summary text, and `"\n\nContinue the task."`.

Back in the loop, `messages` now points at the new list, and `continue` makes the next model call with it. The old list is never sent again. The summary call is not counted as a turn, so it does not use up `MAX_TURNS`. The harness does not check the summary's `stop_reason`; a summary that hits the 4,000-token cap goes on cut short.

<Callout kind="note" title="What a summary loses">
  The fresh conversation knows only what the summary says. The exact contents of files the model read are gone, so it reads them again if it needs them. That is why the request asks for the files touched and what is left to do: those are what the model needs to pick up the work.
</Callout>

## Try it

Force a compaction with a fake model, so it costs nothing. Save this as `harness/python/compact_demo.py`:

```python
from types import SimpleNamespace
import harness

harness.CONTEXT_BUDGET = 1_000  # tiny budget, so the first tool turn goes over it

def reply(stop_reason, block, input_tokens):
    return SimpleNamespace(content=[block], stop_reason=stop_reason,
                           usage=SimpleNamespace(input_tokens=input_tokens, output_tokens=50))

def text(s):
    return SimpleNamespace(type="text", text=s)

def fake_model(messages, **overrides):
    print(f"call: {len(messages)} messages, overrides {overrides}")
    if overrides:  # compact() is asking for the summary
        return reply("end_turn", text("Goal: list the workspace. Done: listed it."), 1_300)
    if messages[0]["content"].startswith("Summary of earlier work"):
        print("  fresh start:", repr(messages[0]["content"][:60]))
        return reply("end_turn", text("All done."), 200)
    ask = SimpleNamespace(type="tool_use", id="toolu_1", name="list_files", input={"path": "."})
    return reply("tool_use", ask, 1_200)

print(harness.run_agent("List the workspace.", call=fake_model))
```

```bash
cd harness/python
python compact_demo.py
```

You should see the first call with 1 message, the `-> list_files` line, then a call with 4 messages and the overrides `{'tool_choice': {'type': 'none'}, 'max_tokens': 4000}`: that is the summary request, the old history plus `ask`. The third call has 1 message again, which starts `Summary of earlier work:`, and the script prints `All done.` In `trace.jsonl`, the `compact` line records `"messages": 3` and `session_end` records `"turns": 2`.

To see it with the real model, give it a bigger file and a smaller budget. Run `cp harness.py workspace/`, set `CONTEXT_BUDGET = 3_000` in `harness.py`, run `python harness.py`, and ask `Read harness.py, then read notes.txt, one at a time, then summarize both.` Then run `grep -E 'compact|model_response' trace.jsonl`. The `input_tokens` grow with each call; the request that carries `harness.py` goes over 3,000, and a `compact` line follows. The next `model_response` is the summary call, the largest of all because it carries the whole history. The one after it is small again. The check only fires after a tool turn, which is why the task asks for a second read. Put the budget back to `150_000` and delete `workspace/harness.py` afterwards.
