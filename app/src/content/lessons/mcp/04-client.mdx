## Concept

A server waits to be asked. The program that asks is the client. In the last two lessons you used our client without reading it. Now you read it.

`mcp/python/client.py` does one command per run and prints one JSON value:

| Command | Does |
|---|---|
| `discover` | Lists the server's name, protocol version, instructions, tools, resources, resource templates and prompts |
| `tools` | Lists each tool with its description, annotations and schemas |
| `call NAME JSON` | Calls a tool |
| `read URI` | Reads a resource |
| `prompt NAME JSON` | Gets a prompt |

This lesson uses stdio: the client starts `read_server.py` as a child process with `--stdio`. A second way to connect, over HTTP, is lesson 7. Everything after the connection is the same, which is the point of a protocol.

### Discovery

<Term t="discovery" /> is how a client learns what a server has. The client lists tools, resources, resource templates and prompts, and reads the server's name and `instructions`. In this revision a server can also answer `server/discover`, but a client does not have to use it. The SDK's client does the probing when it connects, and the result is the `protocol_version` the command prints.

### Calls and errors

A call has two ways to fail, and the client must tell them apart:

- A **tool error** is a normal result with `isError: true` and a text message, such as `limit must be 1 to 20`. The model can read it. Our client prints it as `{"error": "..."}`.
- A **protocol error** is a JSON-RPC error: an unknown method, bad parameters, or a missing resource. The SDK raises it, and the client turns it into a message.

### When a server needs an answer

A server in this revision cannot send the client a question. When `lumen-ops` needs a person to confirm a write, it answers the call with an <Term t="InputRequiredResult" /> that holds the question. The client asks, then sends the same call again with the answer attached. The SDK's `Client` runs those rounds. What the client supplies is the callback that produces the answer. Lesson 8 builds the server side, and lesson 5's agent uses a scripted answer.

The client's own answer is only a claim. A server cannot tell a person from `--yes`. That is why a write needs more than a "yes" over the wire.

## The code

Section 2 connects.

<CodeTabs source="mcp-client" section={2} />

- The HTTP lines in this section are covered in lesson 7.
- `callback = elicitation_callback(answer or deny)` is built first. Passing it to `Client(..., elicitation_callback=callback)` is what declares the elicitation capability.

Section 3 discovers.

<CodeTabs source="mcp-client" section={3} />

- `normalise_schema(schema, defs)` keeps only `type`, `properties`, `required`, `items` and `additionalProperties`. Everything else, such as `title`, `default` and `$defs`, is SDK decoration.
- `if "$ref" in schema: return normalise_schema(defs[...], defs)` follows a reference, so a nested type prints in full.
- `sorted(value)` on `required` and `sorted(t.name for t in tools.tools)` keep the output in a fixed order. Python and Go must print the same bytes.
- `async def discover(client)` calls four list methods and reads `client.server_info`, `client.protocol_version` and `client.instructions` for the rest.

Section 4 calls.

<CodeTabs source="mcp-client" section={4} />

- `result = await client.call_tool(name, arguments)` is the whole call. The SDK builds the request with the right `_meta`.
- `if result.is_error:` takes the first text block as the message, or `<no text>` when there is none.
- `return {"structured": result.structured_content}` is the success shape.
- `except MCPError as e: return {"error": str(e)}` in `read` and `prompt` is where a protocol error becomes a message.

Section 5 answers input-required rounds.

<CodeTabs source="mcp-client" section={5} />

- `async def deny(message) -> bool` is the default answer. A client with no way to ask declines.
- `ask_terminal(...)` writes the question to stderr, so stdout stays clean JSON, and reads one line. Only `y` or `yes` accepts. If stdin is closed it declines, because nobody can answer.
- `props = (params.requested_schema or {}).get("properties", {})` reads the form the server sent. The callback accepts only a form made of yes-or-no fields.
- `if any(p.get("type") != "boolean" for p in props.values()): return ElicitResult(action="decline")` declines a form it cannot fill, rather than guessing.

## How Go does it

The Go tab has the same six sections, in the same order. It exists to prove that a second client, on the other SDK, reads the same servers the same way. Three differences are worth knowing.

- Flags go before the command: `go run ./client -stdio discover`. Go's `flag` package stops at the first argument that is not a flag.
- Go decodes every JSON number as a `float64`, so `1` and `1.0` look alike. The Python client has `canon`, which prints an integral float as an integer, so the two match.
- Go's annotation struct cannot say a hint is absent, so both clients drop `readOnlyHint` and `idempotentHint` when they are false.

## Try it

Run these from the repo root. Everything here is free.

Discover the server over stdio. You should see `"protocol_version": "2026-07-28"` and `"server": "lumen-read"`:

```bash
.venv-mcp/bin/python mcp/python/client.py --stdio discover
```

Call a tool, and then call it from Go. The two commands print the same bytes. We checked by piping both into `md5` and got `b0a7e0fab66d59fd1c32497fbabb1392` each time:

```bash
.venv-mcp/bin/python mcp/python/client.py --stdio call search_tickets '{"query": "charged twice", "limit": 2}'
cd mcp/go && go run ./client -stdio call search_tickets '{"query": "charged twice", "limit": 2}'
```
