## Concept

Tools are not the only thing a server can offer. Two more kinds exist, and they answer a different question: who decides?

### Resources

An <Term t="MCP resource" /> is data with an address. The client lists them (`resources/list`) and reads one by its URI (`resources/read`). The application decides what to read. The model is not asked.

`lumen-read` has two:

- `lumen://reports/eval` is a fixed address. It holds the eval scores from the LLMs track, taken from `llms/data/inspect_summary.json`: four runs (`v1_basic`, `v2_rules`, `v3_examples` and `judge`) with each metric's lab score and Inspect score.
- `lumen://tickets/{id}` is a <Term t="resource template" />: a pattern with a hole in it. `lumen://tickets/t001` is one ticket. Clients find templates with `resources/templates/list`.

A resource carries a `mimeType`, here `application/json`, so a host knows how to show it. Results of reads also carry `ttlMs` and `cacheScope`, which tell a client how long it may keep the answer. Ours say `"ttlMs": 0` and `"cacheScope": "private"`: do not reuse it, and do not share it between users.

A resource that does not exist is a protocol error with the message `unknown ticket: t999` and the code -32602 (INVALID_PARAMS). The 2026-07-28 revision uses -32602 for this (it was -32002). Both Lumen servers send it, and the shared contract checks the code as well as the message.

### Prompts

An <Term t="MCP prompt" /> is a template a person picks, such as a slash command in a chat app. The client lists them (`prompts/list`) and fetches one with its arguments (`prompts/get`). The result is a list of messages to put into the conversation.

`lumen-read` has one, `review_ticket(id)`. It asks the model to fetch the ticket, check that its category and priority fit, and draft a short reply. It does not contain the ticket. The ticket arrives later, from the `get_ticket` tool, in `untrusted_body`. Keeping the customer's words out of the prompt means they never sit in the instruction itself.

### Which one?

| You want to… | Use | Because |
|---|---|---|
| let the model look something up or do something | a tool | the model chooses it, by name and description |
| give the host data to show or attach | a resource | the application chooses it, by address |
| hand a person a ready-made way to start a task | a prompt | the person chooses it, by name |

The same ticket is both a tool (`get_ticket`) and a resource (`lumen://tickets/t001`). They return the same JSON from the same code. The difference is who is allowed to ask.

The resource result had no `structuredContent` and no `isError`: a resource is plain content, not a tool result. The prompt result was one `user` message that tells the model to call `get_ticket` and to treat `untrusted_body` as data.

## The code

Section 3 holds the resources.

<CodeTabs source="mcp-read" section={3} />

- `@mcp.resource("lumen://tickets/{id}", mime_type="application/json")` registers a template. The `{id}` in the address is passed to the function as `id`.
- `return json.dumps(tickets.get(id), ensure_ascii=False)` returns the same ticket JSON that `get_ticket` does.
- `raise MCPError(INVALID_PARAMS, err_unknown(id)) from None` turns a missing id into the fixed message with the code -32602. The SDK would turn a plain `ResourceError` into -32603 (internal error), which is not what the spec says, so the server raises the protocol error directly, as the prompt does.
- `@mcp.resource("lumen://reports/eval", ...)` has no hole in its address, so it is a plain resource.
- `return json.dumps(eval_summary(), ensure_ascii=False)` reads the summary file on every call. The server keeps no copy.

Section 4 holds the prompt.

<CodeTabs source="mcp-read" section={4} />

- `@mcp.prompt()` registers `review_ticket`. Its argument `id` becomes the prompt's one required argument.
- `if not TICKET_ID.match(id)` rejects anything that is not `t` and three digits before the lookup runs, so the argument is never used as a path or a query.
- `raise MCPError(INVALID_PARAMS, err_unknown(id))` is used instead of `ValueError`, because the SDK would wrap a `ValueError` and change the text.
- `f"Review ticket {id}. Fetch it with the get_ticket tool. ..."` is the whole prompt. Only the validated id is inserted; no ticket text is.

## How Go does it

The Go tab shows the same two sections. The one thing worth reading is the error. The Go SDK has a ready-made "resource not found" error, but its message is the generic `Resource not found`. The contract needs `unknown ticket: t999`, so section 1 of the Go server defines `rpcError`, which builds a `jsonrpc.Error` with code `jsonrpc.CodeInvalidParams` (-32602) and the fixed text. The resource template and the prompt both use it. The result on the wire is the same as Python's, message and code.

## Try it

Run these from the repo root. All are free.

Read one ticket as a resource. You should see `"mimeType": "application/json"` and the ticket under `json`:

```bash
.venv-mcp/bin/python mcp/python/client.py --stdio read lumen://tickets/t001
```

Read the eval report. You should see four runs: `v1_basic`, `v2_rules`, `v3_examples` and `judge`. For `v2_rules` the lab and Inspect scores match (`category` 1, `priority` 0.9611):

```bash
.venv-mcp/bin/python mcp/python/client.py --stdio read lumen://reports/eval
```

Read a ticket that is not there. You should see `{"error": "unknown ticket: t999"}` on stdout. A line from the SDK about the failed read also goes to stderr:

```bash
.venv-mcp/bin/python mcp/python/client.py --stdio read lumen://tickets/t999
```

Fetch the prompt. You should see one `user` message that starts `Review ticket t001.`:

```bash
.venv-mcp/bin/python mcp/python/client.py --stdio prompt review_ticket '{"id": "t001"}'
```

Give it a bad id. You should see `{"error": "unknown ticket: x"}`:

```bash
.venv-mcp/bin/python mcp/python/client.py --stdio prompt review_ticket '{"id": "x"}'
```

Last, look at the ticket that is a trap. `t061` is the test ticket for lesson 11. Fetch it and read `untrusted_body`: it holds a how-to question, then text that tells whoever reads it to relabel tickets. The server returns it exactly as written, inside the one field, and nothing in the structure of the result changes:

```bash
.venv-mcp/bin/python mcp/python/client.py --stdio call get_ticket '{"id": "t061"}'
```

<Callout kind="warning" title="A resource is also untrusted">
  The ticket resource carries `untrusted_body` too. A host that attaches a resource to the model's context is putting a customer's words in front of it. The label on the field is the same in both places for that reason.
</Callout>
