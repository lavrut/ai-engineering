## Concept

The cache stage answers a call from a store when the same call was answered before. A hit costs nothing and takes no time: no route, no limiter, no upstream. That is the whole appeal, and the whole difficulty is the word "same".

### What counts as the same call

The course's gateway keeps an exact-body response cache. Its <Term t="cache key" /> is a hash of the request's path and its body bytes, as the caller sent them. Only a `POST` to `/v1/messages` is looked up. Two calls share a key only when every byte of their bodies matches: the model, the system prompt, every message, `max_tokens`, the tools. One different character, and it is a different call.

That is strict on purpose. A looser key, say one that ignored the last message, would hand a caller an answer to a question it did not ask. An exact match can only be wrong when the world changed between the two calls, which is what the time to live is for. Section 3 of `infra/gateway.yaml` is one line, `cache: {ttl_s: 3600, skip_tools: true}`: a stored answer is good for 3600 seconds, an hour, and then the next lookup finds it expired.

### What the cache will not store or serve

Two rules keep agent traffic out of the cache.

- **A request that carries tools is skipped.** With `skip_tools: true`, the stage never looks it up, and the trace says `the request carries tools`. An agent sends its tools with every step of its loop, so this skips most of an agent's traffic.
- **Only an `end_turn` answer is stored.** An answer that stopped on `tool_use` asks the caller to run a tool and come back. The caller acts on it. Replaying a stored one would repeat a step the agent already took, and the next request carries the tool's result anyway.

The second rule holds even with the first turned off. With `skip_tools: false`, a request with tools is looked up, but its answer is stored only if it ended the turn. The Try it shows what that changes in the course's traffic: nothing.

The fixture cases pin both rules: in `cacheable_hit` an `end_turn` answer stored 60 seconds earlier is served, and in `tool_call_skip` the same stored answer is skipped, because the request carries tools.

### The real hit picture

The capstone replays all 957 calls through the cache. It answers 20 of them, a hit rate of 0.0209. All 20 are repeats across sets, and none is a repeat within one:

- 19 hits are in the Go patterns set, `patterns-go`, out of its 56 calls. The Go twin builds its requests from the same tickets as the Python patterns set, byte for byte, and the Python set ran first, so its tool-free answers were already stored.
- 1 hit is in the Go desk, `desk-hand-go`, out of its 188 calls, for the same reason: the Python hand-built desk ran first.

Within the two patterns sets there are 6 repeats of a call the same set already made. Every one of them carries tools, so the cache skips it. In production that is the usual picture: an exact-body cache earns its keep on traffic that really repeats, such as the same question asked by many users or a batch job run twice, and does little for an agent at work.

### The other cache: the API's prompt cache

The model API has a cache of its own, the prompt cache, and it works the other way round. It does not skip the call. It notices that a request starts with the same long prefix as a recent one, such as a system prompt and a tool list, and bills the part read from its cache at a tenth of the input price. Writing a prefix into the cache costs 1.25 times the input price. A caller asks for it by marking where the prefix ends.

The capstone's traffic shows it. Of the four desks, only the Claude Agent SDK desk marks its prefixes, and its recorded usage holds 502,680 input tokens read from the prompt cache and 149,144 written to it. The other three desks show none. The gateway's ledger prices those tokens at the API's multipliers, so they count in lesson 5's spend at the rate the SDK desk really paid.

The LLMs lab is the case each cache handles differently. It sends the same system prompt with each of its 60 tickets, and only the ticket text in the user message changes. To the response cache those are 60 different bodies and 60 misses. To a prefix cache they are one shared start that could be read again at a tenth of the price. The lab marks nothing for caching, so it paid full price for that start every time.

## The code

The cache stage is section 4 of `infra/python/stages.py`.

<CodeTabs source="infra-stages" section={4} goSection={4} />

- `key = cache_key(req.path, req.body)` hashes the path and the body bytes as received. The body is never parsed and printed again first, so the key is the caller's own bytes.
- `if cfg.cache.skip_tools and (req.json or {}).get("tools"):` skips a request with tools before any lookup. An empty tool list counts as no tools.
- `if age >= cfg.cache.ttl_s:` drops an answer past its time to live, and the lookup is a miss that says how old it was.
- `if e.stop_reason != "end_turn":` refuses to serve a stored answer that did not end the turn. The chain never stores one, so this guards against a cache file written by something else.
- `return decision("cache", "hit", f"stored {age:.0f}s ago", key=key)` is a hit. The chain then answers from the store and books the call at $0.

Storing happens in the chain, after the upstream answered: `if cache_verdict == "miss" and up.status == 200 and stop_reason(up.headers, up.body) == "end_turn":`. A skipped call is never stored.

The config line the stage reads is section 3 of `infra/gateway.yaml`.

<CodeTabs source="infra-config" section={3} pythonOnly />

- `ttl_s: 3600` is the time to live, in seconds of the gateway's clock. In the capstone that clock is replay time, so the first hit, in `desk-hand-go`, says `stored 333s ago`: the Python desk's answer was 333 seconds of recorded traffic old.
- `skip_tools: true` is the first rule. The second, `end_turn` only, has no setting.

## How Go does it

The Go twin's section 4 makes the same three decisions, with the same detail strings. Two lines show what matching Python takes.

- `if cfg.Cache.SkipTools && truthy(req.body().MustGet("tools")) {` needs a helper, because Go has no truthiness. Python's `.get("tools")` is false for a missing key, `None` and an empty list alike, and `truthy` gives the same answer for each, so both languages skip the same requests.
- `reason = "None"` fills in a missing stop reason with the word Python prints for `None`, so a stored answer with no stop reason produces the same detail line in both.
