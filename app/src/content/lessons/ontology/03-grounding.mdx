## Concept

<Term t="grounding" /> an AI system in an ontology means two things: its artefacts come from the ontology, and its outputs are checked against it. This lesson does both with Lumen's: it generates three artefacts and compares them with the hand-written ones the course already ships, then validates every saved model answer in the course.

### Three generated artefacts

`generate.py` reads only `ontology/lumen.yaml` and builds:

- **The definitions** a triage prompt needs: one line per category, then one per priority, in the guide's order, each the individual's `definition`.
- **The JSON schema** for a triage answer: `category` and `priority` as enumerations of the individuals, a free `reply`, nothing else allowed.
- **The `label_ticket` tool definition**: the ticket `id` with the `Ticket` id property's pattern, and the `label` as an enumeration of the categories.

### Where the hand-written ones drift

Each is compared with what the course already uses, and the difference is a stated fact, pinned by a test, never a failure:

- **The definitions** against the rule text of the `v2_rules` prompt. Both name every category and every priority. They differ in wording on every line: the prompt paraphrases the guide in 14 lines and folds the tie-breakers in, and the generated text is the guide's own wording in 10 lines, one per individual. The `v3_examples` prompt's rule lines are the same as `v2_rules'`, so one comparison covers both.
- **The JSON schema** against the lab's `TRIAGE_SCHEMA`. They differ only in enum order. The lab lists `billing` first and the priorities from `low` to `urgent`. The generated schema lists `outage` first and the priorities as `urgent`, `high`, `low`, `normal`: the guide's decision order. Same values, same required fields, no extra fields in either.
- **The tool** against the MCP server's `label_ticket`. The server declares `id` and `label` as plain strings and checks the label at runtime, answering `label must be one of: billing, bug, account, how_to, feature_request, outage` when it is wrong. The generated tool declares the pattern on `id` and the six labels on `label`, so a model sees the allowed values before it calls. The server should keep its runtime check either way: a schema guides a caller, and a server cannot trust one.

The course does not change the other tracks' files. If it did, the generated versions would replace the hand-written ones, and the next change to a definition would reach every prompt, schema and tool at once.

### Validating what the models said

The LLMs track saved every triage answer, and the agents track saved every tool call. `grounding.py` reads them back and validates each as a partial `Ticket`, the `--partial` mode of lesson 2: the fields an answer carries are checked, and a rule runs when every field it reads is present. Nothing is called.

That is 700 records from 16 sources: 640 saved triage answers in 12 response files from the LLMs track, and 60 `label_ticket` calls in the 4 recorded agent desks. They hold 7 violations, every one of them `feature_request_never_above_normal`:

- 2 from Haiku on the `v1_basic` prompt, on `t029` and `t055`;
- 4 from Opus and Sonnet on `v1_basic`, one per model and effort, all on `t029`;
- 1 from the fine-tuned Qwen model with LoRA, on `t055`.

Each is a feature request answered `high`. Both tickets name a business impact, a large evaluation and a renewal, and the guide says that makes a feature request `normal`, never more. Zero violations came from `v2_rules` or `v3_examples`, which state the rule, and zero from the agents desks. `v1_basic` states no rule at all: it is two sentences: who the model is, and a request for a category, a priority and a reply.

The desks' zero needs a word. A `label_ticket` call carries a category and no priority, so the one checkable rule cannot run on it. Each desk's records list 25 constraints left to a person, the 24 manual ones and the checkable one, where a triage file lists 24. The validator says so instead of counting the rule as passed.

## The code

The schema is built from the individuals, in their order.

<CodeTabs source="ontology-generate" section={2} />

- `"enum": _names(onto, "Category")` lists the category ids sorted by `order`, so the schema carries the guide's decision order without anyone typing it.
- `"additionalProperties": False` keeps the answer to the three fields, as the lab's schema does.

The tool definition takes the id's pattern from the `Ticket` property.

<CodeTabs source="ontology-generate" section={3} />

- `id_prop["pattern"] = onto.properties["id"]["pattern"]` copies the property's pattern, so the tool and the dataset agree on what a ticket id looks like.
- `"label": {"type": "string", "enum": _names(onto, "Category")}` is the same list the schema uses, from the same place.

The validation is section 2 of `grounding.py`.

<CodeTabs source="ontology-grounding" section={2} />

- `fields = ("category",) if rec.get("kind") == "label" else ("category", "priority")` is why a label call is never charged with a missing priority.
- `found = O.validate(onto, ticket, "Ticket", partial=True)` is lesson 2's validator in partial mode.
- `manual[m] = manual.get(m, 0) + 1` counts each manual constraint once per record, so the file says how many records a rule applies to rather than listing it hundreds of times.

<Callout kind="note" title="Valid is not right">
  A record with no violation can still carry the wrong label. The validator catches answers that break a rule the ontology can check. Whether `bug` was the right category for a ticket is the LLMs track's eval, against the gold labels.
</Callout>

## Try it

Check that the generated artefacts and the validation still match what built them:

```bash
.venv-ontology/bin/python ontology/python/generate.py --check
.venv-ontology/bin/python ontology/python/grounding.py --check
```

You should see:

```text

validation.json: up to date
```
