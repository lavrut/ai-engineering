## Concept

Every track in this course says what a support ticket is. The labelling guide defines each category in words. The triage prompts say it again, in shorter words. The lab's JSON schema lists the categories, and so does the MCP server's `label_ticket` tool, and so do the data contracts. Nobody checks that they all say the same thing. This track writes the facts down once and checks every other artefact against them.

### Four layers of saying what things are

Four words come up whenever a team tries to pin down what its data means. Each one adds something to the one before.

- A <Term t="taxonomy" /> names things and sorts them: a controlled vocabulary, perhaps a hierarchy. The ML track's category map is one. It lists the complaint products, and nothing about what a product is.
- A <Term t="schema" /> adds fields and types: a ticket has a `category`, a string from a closed list, and it is required. The data contracts are schemas, with quality rules on top.
- An <Term t="ontology" /> adds meaning: classes with definitions, the relations between them, named members in a set order, and the rules that hold. "A ticket has exactly one category, and a feature request is never above normal" is ontology, not schema.
- A <Term t="knowledge graph" /> holds the facts themselves, typed by an ontology: this ticket, raised by this customer, about this outage. The ontology says what kinds of thing and link may exist; the graph says which ones do.

Lumen's ontology is a YAML file, `ontology/lumen.yaml`. It has 7 classes, 5 relations and 16 individuals, and it is the third rung.

### The standards it borrows its shape from

Ontologies have standards, published by the W3C. The file is in their shape, so here is what each section corresponds to:

- `classes`, with an optional `subclass_of`, corresponds to classes in <Term t="RDFS" /> and <Term t="OWL" />: `rdfs:Class` and `owl:Class`, joined by `rdfs:subClassOf`.
- `properties` corresponds to OWL datatype properties, each with an `rdfs:domain` and an `rdfs:range`. Its `cardinality` is what OWL states as a cardinality restriction.
- `relations` corresponds to OWL object properties: a named edge from one class to another.
- `individuals` corresponds to <Term t="SKOS" /> concepts: a preferred label and a `skos:definition` for each category and priority. The guide's decision order is closest to a SKOS ordered collection.
- `constraints` corresponds to <Term t="SHACL" /> shapes: rules a record must meet, checked by a program. SHACL has no kind for a rule a program cannot check. This file lists those too, as `manual`, so the gap stays visible.

The section names are the course's own, not the standards'. The file is plain YAML, not OWL or RDF, and no standard's tool reads it. Naming the standards means a reader who meets a real OWL file or SHACL shape recognises each part under its own name.

### Where ontologies sit beside LLMs today

A language model has read a great deal about support tickets, but it has no fixed meaning for Lumen's `outage`. The prompt gives it one. Teams that run models in production keep that meaning in one place and feed it to the model in four ways:

- **Before the call**, the definitions go into the prompt. If they are generated from the ontology, every prompt says the same thing.
- **At the call**, the ontology's closed lists shape the structured output schema and the tool's input schema, so the model can only return a known value.
- **After the call**, the answer is checked against the rules. A rule break is caught and counted, not shipped.
- **Around the call**, a knowledge graph typed by the ontology feeds facts into the context. Retrieval over a graph is often called GraphRAG.

The traffic also runs the other way: models now draft ontologies from documents, and a person reviews what they drafted. An ontology cannot make a model right. A label that breaks no rule can still be the wrong label. What it gives is one place where the meaning lives, and a check that catches the answers that break it.

<Callout kind="note" title="The tools you would use at work">
  Production teams rarely hand-build this. Protégé is the usual editor for OWL ontologies. `rdflib` reads and writes RDF in Python, and `pySHACL` checks data against SHACL shapes. An OWL reasoner such as HermiT infers class membership and finds contradictions. Triple stores such as Apache Jena hold a knowledge graph and answer SPARQL queries over it. This track names them and installs none: the loader, the generator and the audit are a few hundred lines of Python you can read end to end.
</Callout>

### What a production ontology stack adds

The track stops where a real stack keeps going. Four things are left out on purpose:

- **Reasoning beyond subclass inheritance.** Here a subclass inherits its parent's properties and constraints, and that is all. An OWL reasoner infers far more, and finds contradictions no one wrote down.
- **A triple store and SPARQL queries.** Here the ontology is a file, and the facts stay in the tracks' own files. Nothing stores them as a graph to query.
- **Live entity linking.** Nothing reads a ticket's free text and links "my team in Berlin" to a customer or "the export" to a feature. The rules that need the text stay `manual`.
- **Changes in other tracks.** The audit reports where an artefact disagrees with the ontology. It never fixes one: the guide, the prompts, the category map and the contracts belong to their tracks.

## The code

The file's first section is its classes.

- `id: Ticket` names the class, and `definition:` says what it is, in one sentence. A class with no definition is a finding: a name nobody explained is a taxonomy entry, not an ontology class.
- `id: Category` is a class too, not a field. Its members, `outage` to `how_to`, are individuals in section 4, each with its own definition and its place in the guide's decision order.
- `id: Customer` is a class no record in the course carries yet. The ontology can name a kind of thing before any data holds one; that is the difference between saying what may exist and saying what does.

## Try it

Set up the track's virtual environment from the repo root. It holds two packages, `pyyaml` and `pytest`:

```bash
python3 -m venv .venv-ontology && .venv-ontology/bin/pip install -r ontology/requirements.txt
```

Load the ontology and run its consistency checks. Then run the four drift checks: each rebuilds a derived file in memory and compares it with the committed one. None of them calls a model, so all of them are free.

```bash
.venv-ontology/bin/python ontology/python/ontology.py check
.venv-ontology/bin/python ontology/python/ontology.py export --check
.venv-ontology/bin/python ontology/python/generate.py --check
.venv-ontology/bin/python ontology/python/grounding.py --check
.venv-ontology/bin/python ontology/python/audit.py --check
```

You should see:

```text
ontology/lumen.yaml: 0 errors, 0 other findings
ontology.json matches
generated.json: up to date
validation.json: up to date
audit.json: up to date
```

The first line says the file is consistent: every range names something that exists, no `subclass_of` loops, no constraint names an unknown class or property. The other four say each derived file still matches what built it. They say nothing about whether the artefacts agree with the ontology; that is the audit's job, in lesson 4.
