## Concept

Lesson 7 changed the prompt and held the model fixed. This lesson holds the prompt fixed and changes the two other things you control: which model runs the task, and how hard it thinks.

### No temperature

Older guides tune `temperature`, a setting for how random the model's word choice is. Current models reject it, per the Claude API docs for the 5.5 models: a request that sends `temperature`, `top_p` or `top_k` gets a 400 error. The lab sends none of them. You cannot switch the model's randomness off, so you measure it instead, with repeats and the noise band (lesson 4).

That leaves two settings worth tuning here: the model and its effort.

### The model

The lab knows three models, with their prices per million tokens in `PRICES`:

| Model | Input | Output |
|---|---|---|
| `claude-haiku-5-5` | $0.10 | $0.50 |
| `claude-sonnet-5-5` | $2.00 | $10.00 |
| `claude-opus-5-5` | $4.00 | $20.00 |

Opus costs 40 times what Haiku costs per token. A bigger model is often more capable, but whether it is better on your task is a question for the eval, not for the price list.

### Effort

Current models can think before they answer: they write reasoning you do not see, then the answer. <Term t="effort" /> sets how much. It goes in the request as `output_config.effort`, with the levels `low`, `medium`, `high`, `xhigh` and `max`.

Thinking is billed as output tokens. It is counted in `usage.output_tokens` like the answer itself, so higher effort costs more even when the visible reply is the same length.

The levels and defaults here are from the same docs. If you send no effort, the model uses its default: `medium` on Haiku 5.5 and Opus 5.5, `high` on Sonnet 5.5. The lab's `default` means exactly that: it sent nothing.

### What was recorded

The approved recording ran Haiku at its default effort, and Sonnet and Opus at `low` and `high`, all on the 40 dev tickets with `v2_rules`. Sonnet and Opus were also recorded with `v1_basic`. Every number below replays from those files.

With `v2_rules` on dev, noise band ±15.8%:

| Model | Effort | Both right | Cost per 1,000 tickets | Output tokens per call |
|---|---|---|---|---|
| Haiku | default | 97.5% | $0.25 | 199 |
| Sonnet | low | 85.0% | $4.26 | 117 |
| Sonnet | high | 87.5% | $5.38 | 229 |
| Opus | low | 95.0% | $9.32 | 158 |
| Opus | high | 95.0% | $10.73 | 228 |

Cost per 1,000 tickets is the recorded tokens of the 40 calls, priced with `PRICES`, scaled up. Every call sent about 1,543 input tokens, so the cost differences come from the price and the output.

### Reading the table

The cheapest configuration is also the top score. Haiku gets 97.5% for $0.25 per 1,000 tickets. Opus at high effort gets 95.0% for $10.73, about 42 times as much.

Do not read that as "Haiku is better than Opus". 97.5% against 95.0% is one ticket out of 40. Even Sonnet low, 12.5 points below Haiku, is inside the ±15.8% band. On quality, this eval cannot tell these configurations apart. On cost it can, because cost is measured exactly.

Effort shows the same pattern. Going from `low` to `high` roughly doubled Sonnet's output tokens and bought 2.5 points. Opus used about 44% more output tokens at `high` and scored the same. Both changes are inside the band.

The models also miss different tickets. Haiku misses `t034`. Both Opus runs miss `t019` and `t033`. Sonnet low misses six, among them `t015` and `t039`. A model change is a different set of mistakes, not only a different score, so read the misses as you did in lesson 7.

### Pick the cheapest that clears your bar

The rule is: **decide the bar first, then pick the cheapest configuration that clears it, measured.**

Set the bar from what the feature needs, before you look at the scores, for example 90% both right. Then every configuration at or above the bar is good enough, and among those, cost decides. Here that is Haiku, by a factor of about 37 over the next one, Opus low.

Three caveats come with this choice:

- **Noise.** The ranking inside the band is not evidence. If two configurations are close to the bar, more tickets would settle it; these 40 cannot.
- **The prompt was chosen with Haiku.** `v2_rules` became the best prompt from Haiku's dev scores (the recording notes in `llms/data/README.md`). A prompt chosen on one model can suit that model best, so a fair test of a bigger model may need its own prompt tuning. With `v1_basic`, the order changes: Opus high scores 72.5% and Haiku 70.0%, again inside the band.
- **Dev only.** Sonnet and Opus were recorded on dev only, so there is no test number for them. Haiku's one test number, 95.0% (lesson 7), is the one to report for the configuration you ship.

## The code

Section 1 is where the models and their prices live.

<CodeTabs source="llms" section={1} goNote="The same constants: taskModel, judgeModel and defaultMode in a const block, and prices as a map[string][2]float64. dataDir is resolved from the source file with runtime.Caller, as Python does with __file__." />

- `TASK_MODEL = "claude-haiku-5-5"` is the model that triages when you pass no `--model`. The table above is why it is Haiku.
- `JUDGE_MODEL = "claude-opus-5-5"` grades the replies. The judge stays on the stronger model (lesson 5): it runs far fewer calls, and a weak judge would make every reply score doubtful.
- `MODE = "replay"` keeps every run free unless you ask for `record` or `live`.
- `PRICES` maps each model to `(input, output)` dollars per million tokens. `call_cost` and `estimate_cost` (section 8) read it, and the app's chart prices its dots with the same numbers. A model missing from `PRICES` stops the run with a `KeyError` while the estimate is made, before any paid call.

Section 3 is what stays fixed when the model changes.

<CodeTabs source="llms" section={3} goNote="The same schemas as nested map[string]any values. In section 4, triage sets the effort with anthropic.OutputConfigEffort(o.effort); an empty string is omitted, so no effort is sent, and the cache key records it as JSON null." />

- `TRIAGE_SCHEMA` is sent to every model, so every model's answer has the same three fields and the same allowed values. A difference in score is the model's, not the format's.
- `"enum": CATEGORIES` and `"enum": PRIORITIES` hold for Haiku, Sonnet and Opus alike, so `grade` in section 5 needs no change per model.

Effort is set in `triage` (section 4), next to the schema:

```python
output_config = {"format": {"type": "json_schema", "schema": TRIAGE_SCHEMA}}
if effort is not None:                      # null effort means: send nothing
    output_config["effort"] = effort
```

- `output_config["effort"]` sits beside `format` in the same `output_config` object. It is not a top-level field.
- `if effort is not None` sends no effort when you pass none, so the model uses its own default. The cache key stores `null`, and the response file is named `..._default.jsonl`.
- The model and the effort are both in the cache key (lesson 4), so each configuration has its own saved answers and they never mix.

<Callout kind="note" title="Cost per ticket, not per token">
  Compare cost on the eval's own calls, not on the price list. Effort changes the output tokens, and a longer prompt changes the input tokens, so the same model can cost twice as much a ticket under different settings. The chart and the table above both price the recorded tokens.
</Callout>

## Try it

Score every recorded configuration on dev with `v2_rules`, from the saved responses. This is free:

```bash
cd llms/python
python triage_lab.py run --prompt v2_rules
python triage_lab.py run --prompt v2_rules --model claude-sonnet-5-5 --effort low
python triage_lab.py run --prompt v2_rules --model claude-sonnet-5-5 --effort high
python triage_lab.py run --prompt v2_rules --model claude-opus-5-5 --effort low
python triage_lab.py run --prompt v2_rules --model claude-opus-5-5 --effort high
```

The `both accuracy` lines read 97.5%, 85.0%, 87.5%, 95.0% and 95.0%, each with `noise band +/-15.8%`.

The report shows no cost. To price the same calls, save this as `llms/python/cost_table.py`:

```python
import triage_lab as T

dev = T.split(T.load_tickets(), "dev")
configs = [("claude-haiku-5-5", None), ("claude-sonnet-5-5", "low"), ("claude-sonnet-5-5", "high"),
           ("claude-opus-5-5", "low"), ("claude-opus-5-5", "high")]
for model, effort in configs:
    lines = [T.triage(t, "v2_rules", model=model, effort=effort) for t in dev]
    both = T.report([T.grade(t, l) for t, l in zip(dev, lines)])["both"]
    dollars = sum(T.call_cost(model, l["input_tokens"], l["output_tokens"]) for l in lines)
    out = sum(l["output_tokens"] for l in lines) / len(lines)
    print(f"{model:<18} {effort or 'default':<8} both {both:.1%}  "
          f"${dollars / len(dev) * 1000:.2f} per 1,000  {out:.0f} output tokens a call")
```

```bash
python cost_table.py
```

```bash
python triage_lab.py run --model claude-sonnet-5-5 --effort medium
```

Replay stops with `error: no saved response for triage / claude-sonnet-5-5 / v2_rules / case t001 (rep 0). Record it: python triage_lab.py record ...`. The effort is part of the key, so `medium` has no answers yet.

Recording it costs money. Adding `--mode record` prints the estimate and asks first: 40 Sonnet calls, `$0.35`, worst case `$0.87`. Opus at `medium` would be `$0.70`, worst case `$1.74`. Before you pay, ask what the result could change. Haiku already clears a 90% bar at $0.25 per 1,000 tickets, and any score between Sonnet's low and high would sit inside the same band.
