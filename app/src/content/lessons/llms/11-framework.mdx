## Concept

You built the triage eval by hand: a dataset, a runner, code graders and a judge. Every part was yours. That is the right way to learn it, and it has a cost. Each new project would need the same parts again.

An <Term t="eval framework" /> is a library that supplies those parts. This lesson runs the same eval through one, Inspect AI, version 0.3.285. Inspect is Python only. The aim is not new numbers. The aim is the same numbers, so you can see what the framework does for you and what it does not.

Here is the lab, section by section, and the piece of Inspect that does the same job:

| Lab section | Inspect |
|---|---|
| 2. Dataset | A dataset of samples: `input` is the ticket, `target` the category, and the priority rides in metadata |
| 3. The task and 4. Model call | A <Term t="solver" /> builds the request. A model API answers it. Here the model API is a replay provider we write |
| 5. Code graders | A <Term t="scorer" /> with `accuracy()` and `stderr()` as its metrics |
| 6. LLM judge | A model-graded scorer that calls the `grader` model role |
| 8. Runner | Epochs repeat each sample (an <Term t="epoch" /> is one pass), and every run is written to a log |

Inspect gives you:

- the dataset and sample format;
- epochs and reducers, which combine the repeats into one score;
- scorers with metrics and standard error;
- logs, and `inspect view` to browse them.

We still own:

- the replay keys, which decide when a saved answer matches a request;
- the cost estimate and the spend cap before any paid run;
- the judge's position check, which asks whether a verdict changes when the rubric moves;
- deciding which numbers matter: which metric, which split, how big a gap counts.

### Replay, again

Inspect knows how to call the Anthropic API. The lab's saved responses are not an Inspect feature, so we write a model API named `replay`. You run it as `--model replay/claude-haiku-5-5`.

It rebuilds the lab's own cache key from the request and reads the saved line. It never makes a paid call. A request with no saved answer is an error that names the lab's record command, as in lesson 4.

## The code

Three sections hold the parts that are not a straight translation. Section 3 is the replay provider.

<CodeTabs source="llms-inspect" section={3} />

- `saved_line(kind, model, prompt_version, effort, key, root)` reads the response file and returns the latest line with that key, as the lab does. No line means `ReplayMiss`, with the record command in the message.
- `parse_judge_message(text, rubric)` recovers the ticket and the reply from the judge message. It finds the known rubric text first, then splits at the first `"\n\nReply:\n"`, because a reply may contain blank lines or the word `Reply:`.
- `@modelapi(name="replay")` registers the class, so `replay/<model>` works on the command line.
- `rep = int((config.extra_headers or {}).get(REP_HEADER, 0))` reads the repeat number. The solver sends it in the `x-replay-rep` header, because a model provider can't see which epoch it is in. No header means rep 0.
- `variant = next((v for v, text in self.prompts["triage"].items() if system == text), None)` finds the prompt version by matching the system message. An edited prompt matches nothing and falls through to the miss.
- `key = triage_key(user, variant, self.model_name, None, rep, self.prompts)` is the lab's own function. The key has one definition.
- `if line.get("error"): raise RuntimeError(...)` turns a saved error line into a sample error. Inspect leaves it out of the score, as the lab does.
- `replay_or_approved(model)` is the gate on the live path. The solver and the judge scorer call it before every request. A `replay/` model passes. Any other model raises `PermissionError`, naming the estimate command, unless `LUMEN_LIVE_OK=1` is set, so a paid run needs a deliberate approval. It also keeps the `x-replay-rep` header away from a paid model.

Section 5 holds the code scorers.

<CodeTabs source="llms-inspect" section={5} />

- `_field_scorer(field)` builds one scorer per field. Category and priority have one right answer, so plain code compares them.
- `parsed = json.loads(completion) if completion else None` parses the reply. A refusal, a cut-off or invalid JSON scores as incorrect, and the reason goes in the score metadata.
- `expected = target.text if field == "category" else state.metadata["priority"]` is where the sample format pays off: the target and the metadata are already there.
- `@scorer(metrics=[accuracy(), stderr()])` is the part Inspect supplies. It computes the mean and its standard error over all samples, and over epochs.

Section 6 holds the judge scorer.

<CodeTabs source="llms-inspect" section={6} />

- `grader = get_model(role="grader")` gets the judge from a model role. The run sets it with `--model-role grader=replay/claude-opus-5-5`, so the same task can point at a live judge with no code change.
- `judge_message(ticket, reply, rubric)` builds the lab's "after" order: ticket, reply, then the rubric.
- `if not reply:` skips a ticket with no triage reply, as the lab does. It returns `graded: False` in the metadata.
- `@metric def graded_mean()` averages only the graded samples. A plain `mean()` would count the skipped ones as fails, and the pass rates would drop below the lab's.
- `@scorer(metrics={rid: [graded_mean()] for rid in RUBRIC_IDS})` gives one pass rate per criterion: `addresses_issue`, `tone` and `no_false_promises`.

Section 7 sets `fail_on_error=0.5` on both tasks. A few saved error lines are left out of the score, as in the lab. An edited prompt makes most samples miss, so more than half error, and the eval fails loudly with the record hint. Inspect's default would stop on the first error, and `False` would hide a total miss behind a "success". Loudly means on screen and in the log's status: `inspect eval` still exits 0 after a failed task, so a CI job should check with `summarize.py`, which exits 1 when a score stops matching.

<Callout kind="go" title="No Go version">
  Inspect is a Python library, and there is no Go equivalent. The lab's Go version in `llms/go/main.go` is unchanged, and it remains the parity check: it gives the same scores from the same saved responses, which Inspect now matches too. So this lesson has no "How Go does it" section.
</Callout>

<Callout kind="warning" title="Replay is not the live path">
  Everything here is free. The live path swaps `replay/` for `anthropic/` in `--model`, and Inspect then calls the API itself. That costs money, and Inspect has none of the lab's cost estimate, approval prompt or run-wide spend cap. So `triage_inspect.py` refuses any model that is not `replay/`, as the task model or the grader, unless `LUMEN_LIVE_OK=1` is set. Price the run first, as the next section shows.
</Callout>

## Try it

### Set up the venv

Install Inspect in its own virtual environment, never in your base Python. From the repo root:

```bash
python3 -m venv .venv-inspect
.venv-inspect/bin/pip install -r llms/inspect/requirements.txt
.venv-inspect/bin/pip install -e llms/inspect
```

The first line of pip installs `inspect-ai==0.3.285` and the lab's requirements. The second installs a tiny package, `llms/inspect/pyproject.toml`, that tells Inspect about the `replay` provider. The command line needs it: Inspect resolves `--model replay/...` before it opens the task file, so without it you get `Model API replay ... not recognized`. Both steps are free, and `.venv-inspect/` is git-ignored.

### Run the evals

Each command replays saved answers. It costs nothing and needs no API key. The log goes to `llms/inspect/logs/`.

```bash
.venv-inspect/bin/inspect eval llms/inspect/triage_inspect.py@triage --model replay/claude-haiku-5-5 -T variant=v1_basic --log-dir llms/inspect/logs
.venv-inspect/bin/inspect eval llms/inspect/triage_inspect.py@triage --model replay/claude-haiku-5-5 -T variant=v2_rules --epochs 3 --log-dir llms/inspect/logs
.venv-inspect/bin/inspect eval llms/inspect/triage_inspect.py@triage --model replay/claude-haiku-5-5 -T variant=v3_examples --log-dir llms/inspect/logs
.venv-inspect/bin/inspect eval llms/inspect/triage_inspect.py@triage_judged --model replay/claude-haiku-5-5 --model-role grader=replay/claude-opus-5-5 --log-dir llms/inspect/logs
```

Look for these scores on all 60 tickets: `v1_basic` 0.9 category and 0.7333 priority, `v2_rules` 1.0 and 0.9611, `v3_examples` 1.0 and 0.9667. The judged run should show `addresses_issue` 0.7, `tone` 0.95 and `no_false_promises` 0.95.

Open the logs in the browser viewer:

```bash
.venv-inspect/bin/inspect view --log-dir llms/inspect/logs
```

To rebuild the table the aid above shows, run all four and write the summary. It exits non-zero if any row stops matching the lab:

```bash
.venv-inspect/bin/python llms/inspect/summarize.py
```

### See a replay miss

This is free. Copy the data, then edit one prompt in the copy:

```bash
cp -r llms/data ~/lumen-inspect
```

Add a few words to the end of the `v1_basic` text under `triage` in `~/lumen-inspect/prompts.json`, then point the provider at the copy with `-M root`:

```bash
.venv-inspect/bin/inspect eval llms/inspect/triage_inspect.py@triage --model replay/claude-haiku-5-5 -T variant=v1_basic -M root=$HOME/lumen-inspect --log-dir llms/inspect/logs
```

The solver still sends the original `v1_basic` text, because it reads the prompts from `llms/data`; `-M root` only points the provider at the copy. The provider's prompt table no longer holds that text, so every sample misses, and the eval stops with `ReplayMiss: no saved response for claude-haiku-5-5: unknown system prompt ... Record it: ../../.venv-llms/bin/python triage_lab.py record ...`. It names the case and the lab's record command, and it never calls the API. The command still exits 0, so read the screen or the log's status, not the exit code.

### The live path (costs money)

Any model that is not `replay/...`, as `--model` or as `--model-role grader=`, calls the API and costs money. Price the run before you run it. This is free and calls nothing:

```bash
.venv-inspect/bin/python llms/inspect/summarize.py --estimate
```

It prints each of the four runs with its calls and dollars, from the lab's `PRICES` and typical tokens per call (`EST_TOKENS`), the same figures the lab's own estimate uses. The `v2_rules` run over 3 epochs is 60 tickets × 3 = 180 Haiku calls. At 900 input and 700 output tokens a call and $0.10 / $0.50 per million, that is 180 × $0.00044 = $0.0792, about $0.08 (worst case $0.20, if every reply uses all 2,000 `max_tokens`). The judged run adds 20 Opus grader calls, about $0.47 (worst case $0.91). Add `--model anthropic/<model>` or `--grader anthropic/<model>` to price another model.

If you accept the cost, approve that one run by putting `LUMEN_LIVE_OK=1` in front of it. Without it the task refuses the paid model, and nothing is called:

```bash
read -rs ANTHROPIC_API_KEY && export ANTHROPIC_API_KEY
LUMEN_LIVE_OK=1 .venv-inspect/bin/inspect eval llms/inspect/triage_inspect.py@triage --model anthropic/claude-haiku-5-5 -T variant=v2_rules --epochs 3 --log-dir llms/inspect/logs
```

`read -rs` takes the key without echoing it, so it never lands in your shell history. The approval is yours, not a prompt: Inspect has no `y/N`. It does have `--cost-limit`, a dollar limit on each sample, and `--token-limit`, but neither is the lab's `--max-cost` cap on the whole run, so hold yourself to the number the estimate printed.

<Callout kind="note" title="When to reach for a framework">
  A framework earns its place when you run many evals, share them with a team, or want logs and a viewer for free. The hand-built lab earns its place when you need to know exactly why a number is what it is. Here you used both: the lab as the check, Inspect as the tool.
</Callout>
