## Concept

A category and a priority each have one right answer per ticket: the label. So a grader for them is one line of code: is the model's answer equal to the label? That grader is exact, free, instant and gives the same grade every time. Use code wherever code can decide, and save the LLM judge (lesson 5) for what it cannot, such as tone.

### Make the answer gradable

An equality check only works if right answers look the same. Asked in free text, a model might write `Billing`, `billing issue`, or "This looks like a billing question." Each is right, and each fails `== "billing"`.

The lab removes the problem with <Term t="structured output" />. The request carries a JSON Schema, and the API makes the reply follow it. The schema gives `category` an `enum` of the six allowed values and `priority` an `enum` of the four. When the model finishes normally, its answer is valid JSON, and both fields are exact strings from those lists.

### Accuracy, three ways

<Term t="accuracy" /> is the share of graded tickets that are right. The lab reports three:

- `category`: the category matches the label.
- `priority`: the priority matches.
- `both`: both match. This is the headline score, because a ticket with the right category and the wrong priority is still handled wrongly.

### When there is no usable answer

Every saved line gets an outcome before it is graded:

| Outcome | What happened | In accuracy |
|---|---|---|
| `ok` | The model finished normally with a JSON answer. | Graded against the label. |
| `refusal` | `stop_reason` is `refusal`: the model declined. | Counted as wrong. |
| `max_tokens` | The reply hit `max_tokens` and the JSON is cut off. | Counted as wrong. |
| `error` | The call failed: a network error, an overloaded API, or no parseable JSON. | Left out. |

A refusal or a cut-off reply is something the model did. A customer would get no triage, so it counts against the model. An error is different: the model never produced an answer, because the request failed. Counting it as wrong would make your accuracy partly a measure of your network. So errors are left out of the share, and the report prints how many there were, so a run full of errors cannot hide.

The recorded run had none of these. Every call ended with `stop_reason` `end_turn`, and the longest reply used 659 of its 2,000 output tokens. The Try it below fakes one of each, so you can watch the arithmetic.

### The confusion matrix

One accuracy hides which mistakes the model makes. A <Term t="confusion matrix" /> counts every pair of (expected, answered). Rows are the label, columns the model's answer. The diagonal holds the right answers; every other cell is one kind of mistake.

Here is the priority matrix for Haiku with `v1_basic` on the 40 dev tickets:

```text
expected      low  normal    high  urgent
low            14       2       0       0
normal          0       6       3       0
high            1       2       6       0
urgent          0       0       1       5
```

The diagonal adds up to 31 of 40, the 77.5% priority accuracy. The other nine are not random. Eight are one step off, and only one `high` ticket fell two steps, to `low`. Five answers are too high, such as three `normal` tickets raised to `high`, and four are too low. The matrix tells you to look at how the prompt separates neighbouring priorities. The accuracy alone could not.

## The code

Section 3 is the shape of the answer. Section 5 grades it.

<CodeTabs source="llms" section={3} goNote="The same schemas as nested map[string]any values. The enums are built from the categories and priorities slices in section 1, so the lists live in one place." />

- `TRIAGE_SCHEMA` is a JSON Schema for one object with three string fields, `category`, `priority` and `reply`.
- `"enum": CATEGORIES` and `"enum": PRIORITIES` allow only the values from section 1. This is what makes an exact match a fair grader.
- `"required"` lists all three fields, so none can be missing.
- `"additionalProperties": False` forbids extra fields, so the answer has exactly this shape.
- `triage()` in section 4 sends the schema as `output_config={"format": {"type": "json_schema", "schema": TRIAGE_SCHEMA}}`.
- `RUBRIC_IDS`, `_VERDICT` and `JUDGE_SCHEMA` do the same for the judge: a pass or fail and a reason for each rubric item. Lesson 5 uses them.

<CodeTabs source="llms" section={5} goNote="grade returns a Grade struct whose Outcome is ok, refusal, max_tokens or error. accuracy picks the field by name from a small map, and confusionMatrix takes [][2]string pairs, writing an empty answer as (none)." />

- `grade(ticket, line)` takes one saved line and its ticket and returns a dict of booleans plus the `outcome`.
- `if line.get("error")` comes first: a failed call is `"error"`, whatever else the line holds.
- `elif line.get("stop_reason") in ("refusal", "max_tokens")` sets the outcome to that stop reason. `call_model` saves `output` as `null` for these, because there is no usable JSON.
- `output = line.get("output") or {}` turns a missing answer into an empty dict, so `output.get("category")` returns `None` instead of raising.
- `category_ok = outcome == "ok" and ...` means a line with no usable answer is never correct, even by accident.
- `both_ok` is `category_ok and priority_ok`.
- `accuracy(grades, field)` drops the `"error"` grades, then divides the right ones by the rest. Refusals and cut-offs stay in the count as wrong.
- `confusion_matrix(pairs)` counts `(expected, predicted)` pairs into `matrix[expected][predicted]`. A missing answer becomes `"(none)"`, its own column.

<Callout kind="note" title="Bad JSON is recorded as an error">
  `call_model` saves invalid JSON as an `error` line, so it is left out of accuracy. With structured output a normal finish should always parse; if `errors` is ever above 0 in a report, read those lines before you trust the score.
</Callout>

## Try it

Print the priority matrix above, then fake a refusal and an error to see how each moves the score. Save this as `llms/python/graders_demo.py`:

```python
import triage_lab as L

dev = L.split(L.load_tickets(), "dev")
lines = {t["id"]: L.triage(t, "v1_basic") for t in dev}   # replay: saved responses, free

pairs = [(t["priority"], (lines[t["id"]]["output"] or {}).get("priority")) for t in dev]
m = L.confusion_matrix(pairs)
print("expected " + "".join(f"{p:>8}" for p in L.PRIORITIES))
for e in L.PRIORITIES:
    print(f"{e:<9}" + "".join(f"{m.get(e, {}).get(p, 0):>8}" for p in L.PRIORITIES))

grades = {t["id"]: L.grade(t, lines[t["id"]]) for t in dev}
print(f"both {L.accuracy(list(grades.values()), 'both_ok'):.1%}")

t002 = next(t for t in dev if t["id"] == "t002")         # a ticket v1_basic gets right
for change in ({"stop_reason": "refusal", "output": None}, {"error": "overloaded", "output": None}):
    g = {**grades, "t002": L.grade(t002, {**lines["t002"], **change})}
    print(f"{g['t002']['outcome']:<8} both {L.accuracy(list(g.values()), 'both_ok'):.1%}")
```
