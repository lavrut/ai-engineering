## Concept

The last workflow pattern puts a check inside the loop. One call drafts a reply. A second call, the judge, grades the draft against written criteria. If the draft fails, the writer gets the judge's reasons and tries again.

"Building effective agents" says this pattern fits when two things hold:

- there is a clear criterion that a second call can check;
- feedback measurably improves the draft.

The Lumen judge reuses the LLMs track's <Term t="LLM judge" /> prompt and its <Term t="rubric" />: three pass-or-fail items, `addresses_issue`, `tone` and `no_false_promises`. The loop stops on the first draft that passes all three, or after `MAX_ROUNDS = 3` judge calls. The last draft is final either way, so the worst case is fixed: one draft, three judge calls and two revisions, six calls in all.

### A cheaper judge, with a cost

In the LLMs track the judge was `claude-opus-5-5`, a stronger model than the one writing the replies. Here the judge runs on the engine's own model, `claude-haiku-5-5`, through the same call as the writer. That makes it cheap, and it is recorded and replayed like any other call.

The cost is independence. A judge on the same model tends to share the writer's blind spots. It also only checks what its rubric asks. It cannot check facts that nobody gave it.

## The code

Section 6 holds the judge and the loop.

<CodeTabs source="agents-patterns" section={6} />

- `got = _json(_text(_ask(run, call, "judge", "judge", _judge_system(load_prompts()), msg)), "judge")` asks the judge through the same `call` as the writer, with the lab's judge prompt.
- `return {r: got[r]["pass"] for r in RUBRIC_IDS}, {r: str(got[r].get("reason", "")) for r in RUBRIC_IDS}` splits the judge's answer into a verdict and its reasons. A reply without a boolean `pass` for each item raises instead.
- `draft = _text(_ask(run, call, "writer", "draft", writer, _ticket_msg(ticket)))` is the first draft.
- `for n in range(max_rounds):` is the cap: one judge call per round.
- `if all(verdict.values()) or n == max_rounds - 1:` stops on the first full pass, or after the last judge call.
- `failed = "; ".join(f"{r}: {reasons[r]}" for r in RUBRIC_IDS if not verdict[r])` collects only the failed items' reasons. The writer sees exactly what to fix.
- `draft = _text(_ask(run, call, "writer", "revise", writer, ...))` revises with the previous draft and the reasons in the message.
- `run.output = {"rounds": rounds, "final": draft}` keeps every draft and verdict, so a reader can see how the reply changed.

<Callout kind="warning" title="Give the judge what it needs to check">
  A judge can only grade what it can see. This one sees the ticket and the draft, so it can check tone and whether the draft answers the question, but not whether the answer is true. If facts matter, give the writer tools that look them up, and give the judge the same facts.
</Callout>

## How Go does it

The Go tab above shows `judge` and `EvaluateOptimize`. Two details differ.

- **Map order.** Go's `verdict` is a `map[string]bool`, and Go iterates a map in a random order. So the Go code never ranges over the map: `for _, id := range RubricIDs` walks the fixed list instead, both to decide whether all passed and to build the failed reasons. The reasons reach the writer in the same order as Python's, so the revision prompt is the same text.
- **Errors as values.** `judge` returns `(map[string]bool, map[string]string, error)`. A judge reply without a boolean `pass` becomes an error that `EvaluateOptimize` returns to its caller, where Python raises `ValueError`. The contract has three such cases: a reply that is not JSON, a missing `pass` and a `pass` that is not a boolean.
