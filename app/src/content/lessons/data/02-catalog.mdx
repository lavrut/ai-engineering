## Concept

A fabric starts with knowing what exists. A <Term t="data catalogue" /> is a list of datasets with the facts a reader needs before opening one: where it lives, how big it is, what its rows look like, who writes it, who reads it, and when it last changed.

### A fixed list, never a crawl

`catalog.py` catalogues 12 datasets from a list written in the code. It never walks the repo looking for data files. Being in the list is a decision: this dataset is shared, and a reader may depend on it. Because the list is fixed, a dataset that goes missing is recorded as `missing`, not silently dropped.

Each dataset is a path or a glob from the repo root. Some datasets are one file, such as the tickets. Others are many: the agents traces are 134 files, one recorded run per file.

### What it records

For each dataset the catalogue records:

- the files, their total size, and the number of rows (a JSONL line, or a whole JSON file where one file is one record);
- a <Term t="schema sketch" />: each field name and the JSON type its values have, read from the first 50 rows of the first file;
- the producer track, and the consumer tracks;
- the contract it is under, if any, and the hash of the last commit that changed its files, stored in full (the explorer shows the first seven characters). Without the repo's full git history, as in a zip or a shallow clone, it is `null`.

A schema sketch is not a contract. The sketch describes the rows that exist today. A contract promises what rows will look like, and says what each field means. The sketch is how you find a dataset worth a contract; the contract is what a reader can rely on.

### Lineage

Lineage is the same facts drawn as a graph: tracks write datasets, and consumers read them. Each edge carries the contract it travels under and the version, when there is one. Follow the edges forward from a dataset and you have the list of everything a change to it could reach.

Lineage also records derivation. The capstone writes `tickets_v2` from `tickets`, so lineage has an edge from one dataset to the other. A change to the v1 tickets reaches the agents eval through the v2 file, even though the eval never opens the v1 file.

Four datasets are under a contract: `tickets`, `tickets_v2`, `complaints` and `agents_traces`. The other 8, such as `model_responses` with its 743 rows in 14 files, are read across tracks with no written promise at all. That is normal for a young fabric: contracts go first where a break would hurt most.

## The code

Section 3 builds the catalogue.

<CodeTabs source="data-catalog" section={3} />

- `for row in rows[:SAMPLE_ROWS]:` reads at most `SAMPLE_ROWS = 50` rows for the sketch. It is a sketch, not a census.
- `if set(kinds) == {"integer", "number"}:` reports a field holding both `1` and `1.5` as `number`, the contract type that accepts both.
- `found = files(root, ds["path"])` expands the dataset's glob. `files` also drops anything git ignores, because a fresh clone would not have it.
- `names = [c["name"] for c in C.load_contract(_contract_file(contracts, ds["contract"]))["consumers"]]` takes a contracted dataset's readers from its contract, so the contract is the one place they are written. A dataset without a contract takes the readers listed beside it in section 1.
- `"missing": not found` is the flag for a listed dataset with no files.

Section 4 turns the catalogue into lineage.

<CodeTabs source="data-catalog" section={4} />

- `edges.append({"from": producer, "to": ds_id, "contract": cid, ...})` is the write edge, from the track to its dataset.
- `if ds_id in sources:` adds the derivation edge. For `tickets_v2` it runs from `tickets`, carrying `tickets.v1`, the contract the migration reads under.
- `readers = [(c["name"], cid, c["version"]) for c in governing["consumers"]]` makes one read edge per consumer, carrying the version that consumer declares. During the capstone, two readers of the tickets sit on two versions, and lineage shows both.

<Callout kind="note" title="One ticket is outside every contract">
  The agents eval scores 13 tickets. Twelve come from the Lumen tickets, which `tickets.v2` governs. The eval reads it as is, and the consumer tests leave it out of every contract check.

## Try it

Rebuild the catalogue and lineage from the files. It writes the same two files that are committed:

```bash
.venv-data/bin/python data/python/catalog.py
```

You should see:


Now ask lineage the capstone's question: which edges touch the tickets?

```bash
.venv-data/bin/python -c 'import json; l = json.load(open("data/data/derived/lineage.json")); [print(e["from"], "->", e["to"], e["contract"], e["version"]) for e in l["edges"] if "tickets" in e["from"] + e["to"]]'
```

You should see:

```text
data -> tickets_v2 tickets.v2 2
llms -> tickets tickets.v1 1
tickets -> mcp-read-server tickets.v1 1
tickets -> tickets_v2 tickets.v1 1
tickets_v2 -> agents-eval tickets.v2 2
```

Read it from the top of the graph down: `llms` writes `tickets` under v1, and the MCP read server reads it under v1. The migration reads `tickets` under v1, and `data` writes `tickets_v2` under v2, which the agents eval reads under v2.
