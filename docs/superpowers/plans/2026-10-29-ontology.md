# Ontology Track Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a four-lesson track in which the learner writes Lumen's ontology, generates the artefacts an AI system needs from it, validates model outputs against it, and audits every other artefact that implies the same facts.

**Architecture:** one hand-built YAML ontology in the shape of the standards; a standard-library Python loader/checker/validator; a generator whose outputs are compared with the course's existing prompt text, output shape and tool schema; a validator over the saved triage responses and the recorded agent tool calls; an audit that compares the ontology with the labelling guide, the prompts, the ML category map and the data contracts, with a gate. Derived JSON feeds three app aids. Other tracks' files are read in place.

**Tech Stack:** Python 3.12 in `.venv-ontology` (pyyaml 6.0.3, pytest), Astro 7 + Preact + Vitest in `app/`.

**Spec:** `docs/superpowers/specs/2026-10-29-ontology-design.md`

## Global Constraints

- Free and offline: no API calls anywhere; tests make no network calls. Never set ANTHROPIC_API_KEY.
- Python runs only in `.venv-ontology` (`python3 -m venv .venv-ontology && .venv-ontology/bin/pip install -r ontology/requirements.txt`); never base Python. Standard library plus `pyyaml==6.0.3` and `pytest>=8` only.
- Other tracks' files are read in place and never modified: `llms/`, `ml/`, `mcp/`, `agents/`, `data/`, `harness/`.
- Ontology sections, exactly, each under a `# ── N. Title` comment: `classes`, `properties`, `relations`, `individuals`, `constraints`. Literal types, exactly: `string`, `integer`, `number`, `boolean`, `date`. Cardinality: `one`, `many`. Constraint kinds: `checkable`, `manual`.
- Finding shape, exactly: `{"level": "error"|"warning"|"manual", "rule": str, "subject": str, "detail": str}`, sorted by `(level, rule, subject)`; a malformed file or a dangling reference is a finding naming the id, never an exception.
- Derived JSON is deterministic (sorted keys, trailing newline), free of absolute paths, under 200 KB in total; every `--check` fails on drift naming the file.
- Every number a lesson states is pinned by a test (prose and quiz); the track's shipped props under 200 KB; the quiz-spread and no-backtick guards apply.
- Lessons follow `docs/STYLE.md`; aids follow the data/agents aids' patterns (tokens only, keyboard, live regions, tables in their own scroll box, 375 px without page scroll).
- Stage explicit paths; never amend; no attribution lines; never commit `.vscode/`, `*.ipynb`, `.venv-*`, `app/dist`, `app/publish`.

## Review Focus

- A ticket whose category is `feature_request` and priority above `normal`: the guide forbids it, and a reasonable learner expects the validator to flag it as a checkable constraint, not a manual one; pinned in Task 1.
- A `subclass_of` cycle (`A → B → A`): `check` reports one finding naming the cycle and still returns, never recursing forever; pinned in Task 1.
- A saved response whose output lacks `priority` (or carries an unknown category): validation counts it under a named violation type rather than skipping it; pinned in Task 3.
- A labelling-guide heading reworded slightly: the audit reports `disagree` with the diff, not `agree` by accident of a loose match, and not `missing`; pinned in Task 4.
- A contract enum that gains a value the ontology lacks (the Data track's `security`): the audit reports `disagree` naming the value; pinned in Task 4.

### Task 1: Lumen's ontology and the loader, checker and validator

**Files:**
- Create: `ontology/requirements.txt`, `ontology/lumen.yaml`, `ontology/python/ontology.py`, `ontology/data/derived/ontology.json`
- Test: `ontology/python/tests/test_ontology.py`, `ontology/python/tests/fixtures/` (small ontologies with each defect)

**Interfaces:**
- Produces: `load(path: Path) -> Ontology` (a dataclass holding the five sections as dicts keyed by id, plus `source: Path`); `check(onto) -> list[Finding]`; `validate(onto, record: dict, cls: str) -> list[Finding]`; `export(onto, out: Path) -> dict` writing `ontology.json` = the five sections normalised (lists sorted by id) for the app; `main(argv)` with `check`, `validate <cls> <jsonl>` and `export [--check]` subcommands.
- Constraint expression language (small, deterministic): `kind: checkable` constraints have `when` and `then` as lists of `{property, op, value}` with `op` in `eq|ne|in|not_in|gt|lt|gte|lte|present|absent`; a record violates when every `when` clause holds and any `then` clause fails. `kind: manual` constraints have only `text` and `source` (the guide rule id).
- The ontology's content (from the files; the implementer reads them): classes `Ticket`, `Category`, `Priority`, `Reply`, `Complaint`, `Product`, `Customer`; properties of `Ticket`: `id` (string, pattern `^t\d{3}$`), `text` (string), `category` (enumeration of the six Category individuals), `priority` (enumeration of the four Priority individuals), `tags` (string, many), `split` (enumeration `dev|test`); relations `Ticket has_category Category`, `Ticket has_priority Priority`, `Reply answers Ticket`, `Complaint about Product`; individuals: the six categories with the labelling guide's C1–C6 definitions and order, the four priorities with the guide's definitions, the products from `ml/data/category_map.json` `categories`; constraints: `checkable` ones over the fields that exist on a ticket record (category and priority in range; `feature_request` never above `normal`, guide line "A feature_request is never above normal"; `outage` implies priority at least `high` if the guide says so: read it), and `manual` ones for every other guide rule (R0 bullets, the C-rule tie-breakers, U1–U4, H*, L*), each carrying the rule id and text.
