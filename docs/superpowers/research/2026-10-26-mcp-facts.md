Spec base: https://modelcontextprotocol.io/specification/2026-07-28/ (index: https://modelcontextprotocol.io/llms.txt)

## 1. Spec version and key changes (2026-07-28 vs 2025-11-25)
- Current revision is 2026-07-28; previous 2025-11-25. [V-src] .../2026-07-28/changelog.md
- Stateless: no `initialize` / `notifications/initialized`. Every request carries `_meta` keys
  `io.modelcontextprotocol/protocolVersion`, `.../clientCapabilities` (required), `.../clientInfo` (SHOULD); results carry
  `_meta["io.modelcontextprotocol/serverInfo"]` (SHOULD). Mismatch -> `UnsupportedProtocolVersionError` (code -32022). changelog.md; basic/versioning.md
- No protocol sessions; `Mcp-Session-Id` removed. `tools/list` etc. may not vary per connection (may vary by auth/scopes).
  Cross-call state = explicit server-minted handles passed as ordinary tool args (basket_id pattern). changelog.md; server/tools.md#stateful-tools
- New required RPC `server/discover` (supportedVersions, capabilities incl. `extensions`, instructions, serverInfo, ttlMs/cacheScope).
  Optional for clients; recommended first on stdio as a legacy-compat probe. server/discover.md
- `subscriptions/listen` replaces the HTTP GET stream and `resources/subscribe|unsubscribe`. Opt-ins: toolsListChanged,
  promptsListChanged, resourcesListChanged, resourceSubscriptions. changelog.md; basic/patterns/subscriptions.md
- Removed: `ping`, `logging/setLevel`, `notifications/roots/list_changed`, SSE resumability (`Last-Event-ID`), `notifications/elicitation/complete`
  and `elicitationId`. Log level is per-request via `_meta["io.modelcontextprotocol/logLevel"]`. changelog.md
- Server-to-client requests are gone. Servers return `InputRequiredResult` (`resultType:"input_required"`, `inputRequests`, opaque
  `requestState`); client retries the SAME request with `inputResponses`. Only allowed on `tools/call`, `resources/read`, `prompts/get`.
  This is "MRTR". basic/patterns/mrtr.md
- Every result has required `resultType` ("complete" | "input_required" | "task" for Tasks ext).
- Tasks moved out of core to extension `io.modelcontextprotocol/tasks` (polling `tasks/get`, `tasks/update`, `tasks/cancel`; `tasks/result`
  and `tasks/list` removed). Extensions generally: `extensions` map in capabilities. changelog.md
- HTTP: required headers `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` (tools/call, resources/read, prompts/get); `x-mcp-header` on tool
  params mirrors to `Mcp-Param-{name}`. Results of list/read ops need `ttlMs` + `cacheScope` ("public"|"private"). changelog.md
- Resource-not-found is now -32602 (was -32002). Spec-reserved error range -32020..-32099 (HeaderMismatch -32020,
  MissingRequiredClientCapability -32021, UnsupportedProtocolVersion -32022). inputSchema/outputSchema accept any JSON Schema 2020-12;
  `structuredContent` may be any JSON value. changelog.md
- Auth minor: RFC 9207 `iss` validation (SHOULD from AS, client MUST validate if present); `application_type` required in DCR;
  credentials keyed by issuer. changelog.md
- Deprecated (still functional; earliest removal = first revision on/after 2027-07-28): Roots, Sampling, Logging, Dynamic Client
  Registration (use CIMD), `includeContext` thisServer/allServers. HTTP+SSE transport also Deprecated. .../2026-07-28/deprecated.md
- JSON-RPC batching: removed back in 2025-06-18 ("Remove support for JSON-RPC batching"); single message per POST in 2026-07-28.
  https://modelcontextprotocol.io/specification/2025-06-18/changelog.md ; transports/streamable-http.md ("body MUST be a single request or notification")
- Legacy/modern "eras": modern = 2026-07-28+, legacy = initialize-handshake versions (<=2025-11-25); dual-era implementations fall back. basic/versioning.md

## 2. Core concepts (exact method names)
- Architecture: host (container/coordinator, consent, LLM integration) creates N clients; each client talks to one server. Spec
  describes MCP as stateless, every request self-contained. https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md
- Messaging is client->server requests only; server never initiates JSON-RPC requests; client never sends responses. transports/index.md
- Tools: `tools/list`, `tools/call`, `notifications/tools/list_changed`; Tool = name, title, description, icons, inputSchema,
  outputSchema, annotations (untrusted unless server trusted). Result: `content[]` (text/image/audio/resource_link/embedded resource),
  `structuredContent`, `isError`. Names 1-128 chars [A-Za-z0-9_.-]. Return in deterministic order. server/tools.md
- Resources: `resources/list`, `resources/read`, `resources/templates/list`, `notifications/resources/list_changed`,
  `notifications/resources/updated` (via subscriptions/listen). Capability `resources` {subscribe, listChanged}. server/resources.md
- Prompts: `prompts/list`, `prompts/get`, `notifications/prompts/list_changed`. server/prompts.md
- Elicitation (client feature): servers ask via an `elicitation/create` entry inside `InputRequiredResult.inputRequests`. Modes `form`
  (flat-object schema; mode optional, default form) and `url` (out-of-band; MUST be used for credentials/secrets). Client declares
  `elicitation: {form:{}, url:{}}` in per-request clientCapabilities. Result `action`: accept/decline/cancel. client/elicitation.md
- Other utilities: completion, pagination, progress (`notifications/progress`), cancellation, caching (ttlMs/cacheScope).
  https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching.md
- Servers should return tools with an "instructions" string in server/discover for LLM guidance. server/discover.md

## 3. Transports
- Two standard transports: stdio and Streamable HTTP. HTTP+SSE (2024-11-05) is Deprecated. transports/index.md; deprecated.md
- stdio: client launches subprocess; newline-delimited JSON-RPC on stdin/stdout, no embedded newlines; stderr for logs; server must
  not write non-MCP to stdout. Cancellation = `notifications/cancelled`. transports/stdio.md
- Streamable HTTP: single MCP endpoint (e.g. /mcp), POST only (GET stream removed). Client Accept must list application/json and
  text/event-stream; server replies with JSON object or request-scoped SSE stream (progress/message notifications then final response).
  Closing the SSE stream = cancel. No resumability: re-issue as new request with new id. Long-lived notifications only through
  `subscriptions/listen` response stream. Bad version -> 400 + UnsupportedProtocolVersionError; unknown method -> 404 + -32601.
  transports/streamable-http.md
- Server MUST validate `Origin` (403 if bad), SHOULD bind to 127.0.0.1 locally, SHOULD authenticate (DNS rebinding). streamable-http.md#security--endpoint
- Python SDK server answered a raw `server/discover` POST with supportedVersions ["2026-07-28"] [V-run].
- Sessions: gone from the spec. SDKs still carry legacy session knobs for old clients (Python `stateless_http`, Go `Stateless`; see 7, 8).

## 4. Authorization (HTTP transports only)
- stdio servers SHOULD NOT use this spec (take creds from env). basic/authorization/index.md
- Roles: MCP server = OAuth 2.1 resource server; MCP client = OAuth 2.1 client; authorization server (AS) separate/possibly co-hosted.
  Based on OAuth 2.1 draft-13, RFC 6750, 8414, 7591, 8707, 9728, 9207, CIMD draft, OIDC Discovery. authorization/index.md
- Discovery: server MUST implement Protected Resource Metadata (RFC 9728). 401 carries
  `WWW-Authenticate: Bearer resource_metadata="https://host/.well-known/oauth-protected-resource", scope="..."`; else client falls back
  to `/.well-known/oauth-protected-resource/<mcp-path>` then root. AS metadata: RFC 8414 or OIDC discovery (client must support both,
  tries path-aware well-known URLs in priority order). authorization/authorization-server-discovery.md
- Client registration priority: (1) pre-registered, (2) Client ID Metadata Documents if AS metadata has
  `client_id_metadata_document_supported: true` (client_id = HTTPS URL with path, doc has client_id/client_name/redirect_uris),
  (3) Dynamic Client Registration (now DEPRECATED), (4) ask user. authorization/client-registration.md
- Tokens: client MUST send RFC 8707 `resource` (canonical MCP server URI) in BOTH authorization and token requests; token in
  `Authorization: Bearer` on every request, never in query string. Server MUST validate the token was issued for it (audience), MUST NOT
  accept/pass through other tokens. 401 invalid/expired; 403 insufficient scope -> step-up flow. authorization/index.md
- PKCE/OAuth 2.1 flow; validate `iss` (RFC 9207) before redeeming code. authorization/index.md
- Extensions: OAuth Client Credentials (`io.modelcontextprotocol/oauth-client-credentials`), Enterprise-Managed Authorization.
  https://modelcontextprotocol.io/extensions/client-matrix.md
- Local test setup needs (my synthesis from the above + SDK/Inspector docs, not stated as one recipe anywhere):
  an AS (any OIDC/OAuth 2.1 server, or the SDK-hosted one) that supports PKCE + `resource` + a registration path; the MCP server
  serving PRM and returning 401+WWW-Authenticate; a client with a loopback redirect URI. Inspector web callback default
  http://127.0.0.1:6274/oauth/callback, CLI/TUI http://127.0.0.1:6276/oauth/callback; flags `--client-id/--client-secret` (pre-registered)
  or `--client-metadata-url` (CIMD). https://modelcontextprotocol.io/docs/2026-07-28/tools/inspector/authorization.md
  Whether the spec permits http://localhost resource URIs for dev: NOT verified (see 11).

## 5. MCP Apps (extension id `io.modelcontextprotocol/ui`)
- Interactive HTML rendered in a sandboxed iframe in the host. https://modelcontextprotocol.io/extensions/apps/overview.md
- Tool declares `_meta.ui.resourceUri` = a `ui://...` URI (path arbitrary). Host can preload it. Resource is a normal MCP resource
  with MIME `text/html;profile=mcp-app`; resource `_meta.ui` may hold `csp` (allowed external origins, deny-by-default) and
  `permissions` (camera/mic...). Tool `_meta.ui.visibility` can be "model"/"app". apps/build.md; ext-apps 2.0.3 package (read)
- Host<->app protocol is a JSON-RPC dialect over postMessage: `ui/initialize`, `ui/message`, `ui/open-link`, `ui/download-file`,
  `ui/notifications/tool-input|tool-result|host-context-changed|...`; app can call server tools through host (`app.callServerTool`).
  Extension spec version in package: "2026-01-26". [V-src] @modelcontextprotocol/ext-apps@2.0.3 dist/src/app.js
- Client advertises `extensions: {"io.modelcontextprotocol/ui": {mimeTypes:["text/html;profile=mcp-app"]}}`. basic/versioning.md
- npm `@modelcontextprotocol/ext-apps` latest = 2.0.3 (node>=20; peers: zod ^4.2, @modelcontextprotocol/{core,client,server} ^2.0.0).
  Server helpers: `registerAppTool`, `registerAppResource`, `RESOURCE_MIME_TYPE` (from "@modelcontextprotocol/ext-apps/server");
  UI side: `App` class (`connect()`, `ontoolresult`, `callServerTool`); also /react and `app-bridge` for building hosts.
  https://modelcontextprotocol.io/extensions/apps/build.md (note: its sample still imports old `@modelcontextprotocol/sdk` -> docs lag the v2 peers)
- Hosts rendering Apps (client matrix, rendered HTML): Claude (web), Claude Desktop, VS Code Copilot, M365 Copilot, Goose, Postman,
  MCPJam, ChatGPT, Cursor, Archestra.AI, PostHog Code. NOT ticked: MCP Inspector, fast-agent, mcpc. Claude Code is not in the matrix
  at all (unverified). https://modelcontextprotocol.io/extensions/client-matrix
- Testing: ext-apps `examples/basic-host` (`SERVERS='["http://localhost:3001/mcp"]' npm start`, http://localhost:8080); for Claude, expose
  via `npx cloudflared tunnel` and add a custom connector (paid plans). apps/build.md
- Python server CAN serve an App. [V-run] mcp 2.3.0 has built-in `mcp.server.apps.Apps`:
  `apps=Apps(); @apps.tool(resource_uri="ui://clock/app.html") ...; apps.add_html_resource(uri, html); MCPServer("x", extensions=[apps])`
  -> tool meta {'ui':{'resourceUri':...}} and resource mime `text/html;profile=mcp-app` confirmed. Docstring says TS and C# ship Apps as a
  separate package. The ext-apps repo's Python qr-server does it by hand with `meta={"ui":{"resourceUri":...}}` (v1 FastMCP API, outdated import).
  https://github.com/modelcontextprotocol/ext-apps/blob/main/examples/qr-server/server.py
- Go server: no Apps helper found in go-sdk v1.8.0 (grep for ui:// / mcp-app empty). It is feasible by hand (Tool and Resource have `Meta`
  `_meta`) but I did NOT run it. The JS package is only needed for the iframe-side `App` (or hand-write the postMessage protocol;
  the UI HTML can be a plain string/file served by any language). apps/overview.md#framework-support

## 6. Tasks (extension id `io.modelcontextprotocol/tasks`)
- Official extension, spec in https://github.com/modelcontextprotocol/ext-tasks ; overview https://modelcontextprotocol.io/extensions/tasks/overview.md
- Opt-in via capability only: client puts `extensions["io.modelcontextprotocol/tasks"]` in per-request clientCapabilities, server in
  `server/discover`. Server decides per request; no per-request flag. Server must not return a task to a client that did not declare it.
- Flow: request (e.g. tools/call) -> `CreateTaskResult` (`resultType:"task"`, taskId, status, ttlMs, pollIntervalMs; created durably) ->
  client polls `tasks/get` -> `input_required` returns `inputRequests`, client answers with `tasks/update` (`inputResponses`) ->
  `completed` (result) | `failed` (error) | `cancelled`. `tasks/cancel` is cooperative. Optional `notifications/tasks` via subscriptions/listen.
- Status values: working, input_required, completed, failed, cancelled (last three terminal).
- Client support: only MCPJam is ticked for Tasks in the client matrix. Python 2.3.0 and Go 1.8.0: no tasks extension code found
  (grep for "io.modelcontextprotocol/tasks" empty) -> a task-based lesson would need hand-rolled handlers or the TS SDK. (negative grep, not exhaustive)

## 7. Python SDK `mcp` 2.3.0 (PyPI, Python>=3.10)
- Big change: FastMCP is GONE in v2. `mcp.server.fastmcp` raises ModuleNotFoundError pointing at the migration guide; high-level API is
  `MCPServer` (`from mcp.server import MCPServer`, also `mcp.server.mcpserver`). Pin `mcp<2` to keep v1 code. [V-src] mcp/server/fastmcp.py in wheel.
  Docs: https://py.sdk.modelcontextprotocol.io/ ; migration https://py.sdk.modelcontextprotocol.io/v2/migration/
- Deps changed: httpx2, mcp-types==2.3.0, pydantic>=2.12, pyjwt[crypto], starlette, uvicorn, sse-starlette. Optional extra `cli` (typer) gives
  `mcp dev server.py` (opens Inspector), `mcp run server.py --transport streamable-http`, `mcp install`. https://pypi.org/project/mcp/2.3.0/
- Server decorators: `@mcp.tool(name,title,description,annotations,icons,meta,structured_output)`, `@mcp.resource("greeting://{name}", mime_type=, meta=)`,
  `@mcp.prompt()`, `@mcp.completion()`, `@mcp.custom_route`. `Context` param injectable; `Resolve/Elicit/Sample/ListRoots` markers for MRTR/elicitation
  (`Annotated[T, Resolve(fn)]`), `RequestStateSecurity`/AESGCM codec for requestState, `extensions=[...]`, `cache_hints`, `subscriptions`.
- Structured output: automatic from return annotation. Pydantic/dataclass/TypedDict -> structured object; primitives are wrapped as
  `{'result': 3}`. [V-run]
- Run: `mcp.run()` (stdio default), `mcp.run("streamable-http", host=, port=, stateless_http=, json_response=, streamable_http_path="/mcp")`,
  `mcp.run("sse")` (deprecated transport still shipped), or ASGI app `mcp.streamable_http_app()` for uvicorn.
- Auth (server): `MCPServer(..., auth=AuthSettings(issuer_url=, resource_server_url=, required_scopes=, validate_token_resource=),
  token_verifier=TokenVerifier)` where `TokenVerifier.verify_token(token)->AccessToken|None` (set AccessToken.resource for RFC 8707 check);
  or `auth_server_provider=` to host an AS in-process. `validate_token_resource` unset warns; default flips to True in 3.0. [V-src]
  Auth (client): `mcp.client.auth.OAuthClientProvider` (+ `TokenStorage` protocol; extensions client_credentials, identity_assertion). [V-src, not run]
- Client: `from mcp import Client, StdioServerParameters`; `Client(url_str)` = Streamable HTTP; `Client(StdioServerParameters(...))` = stdio;
  `Client(server_instance)` = in-memory (great for tests). Methods: list_tools/call_tool/list_resources/read_resource/list_prompts/get_prompt/
  listen/subscribe_resource; properties protocol_version, server_info, server_capabilities. Handles InputRequired rounds automatically.
- Minimal server (server.py) [V-run, stdio and HTTP]:
    from mcp.server import MCPServer
    mcp = MCPServer("Demo")
    @mcp.tool()
    def add(a: int, b: int) -> int: return a + b
    @mcp.resource("greeting://{name}")
    def greeting(name: str) -> str: return f"Hello, {name}!"
    @mcp.prompt()
    def review(code: str) -> str: return f"Please review:\n{code}"
    if __name__ == "__main__": mcp.run()                      # or mcp.run("streamable-http", host="127.0.0.1", port=8765)
- Minimal client [V-run: negotiated protocol 2026-07-28 over both transports]:
    async with Client("http://127.0.0.1:8765/mcp") as c:                     # or Client(StdioServerParameters(command=sys.executable, args=["server.py"]))
        r = await c.call_tool("add", {"a": 1, "b": 2}); print(r.structured_content)   # {'result': 3}
  Source: README of mcp 2.3.0 (https://pypi.org/project/mcp/2.3.0/) ; my runnable copies: scratchpad/pytest_mcp/{server,client,client_stdio,apps_demo}.py
- Venv used: scratchpad/venv (base Python untouched).

## 10. Security guidance
Primary: https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices.md (sections: Confused Deputy, Token
Passthrough, SSRF, State Handle Hijacking, Local MCP Server Compromise, OAuth Authorization URL Validation, stdio in proxy scenarios,
Mix-Up Attacks, Localhost Redirect URI Impersonation, CIMD Trust Policies, Scope Minimization).
- Confused deputy: MCP proxy servers using a static upstream client_id MUST get per-client user consent before forwarding to third-party AS
  (best_practices #confused-deputy-problem).
- Token passthrough is explicitly forbidden: server must not accept tokens not issued for it nor forward client tokens upstream; validate
  audience (authorization/index.md; best_practices #token-passthrough).
- State-handle hijacking (new, caused by statelessness): handles are names, not credentials; authorize on every call; use unguessable ids.
- Tool results/annotations: tool annotations are untrusted unless the server is trusted; serverInfo is self-reported, not for security
  decisions; servers MUST validate inputs, access-control, rate-limit, sanitize outputs; clients SHOULD confirm sensitive ops, show tool
  inputs, validate results before passing to the LLM, log usage. server/tools.md#security-considerations ; server/discover.md
- Elicitation: never request secrets via form mode (use URL mode); client UI must show which server asks. client/elicitation.md
- Local servers: sandbox, show full startup command and require consent; Streamable HTTP: Origin check + bind localhost.
- "Prompt injection via tool results" and "tool poisoning" are NOT named anywhere in the spec/best-practice pages I read (grep for
  inject/poison empty); the closest normative text is the bullets above. Treat the named-attack framing as course material, not spec citation.
