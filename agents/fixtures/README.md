# Shared contract: `contract.jsonl`

The Python and Go hand-built patterns and desks (`agents/desk/python/patterns.py` and `supervisor.py`,
`agents/desk/go`) must both pass every case. The file is generated by `.venv-agents/bin/python agents/fixtures/gen_contract.py --write` (`--check` exits 1 if it is stale);
expectations come from running the Python patterns against the scripted replies. Edit the generator, never the JSONL.
Same conventions as `mcp/fixtures/README.md`: one JSON object per line, sorted keys, ASCII-escaped.

## Line format

`{"name", "pattern", "ticket_id", "scripted", "expect"}`: 15 base cases, one per pattern (`chain`, `route`, `parallel`,
`orchestrate`, `evaluate_optimize`) per sample ticket (`t001`, `t007`, `t061`, looked up in `agents/evals/tickets.jsonl`), then extra cases (leading prose before the JSON, route
normalisation, an unknown lookup tool, and the error paths below), then the desk cases (section "Desks" below).

- `scripted`: the model's replies in call order. A string is one text reply. `{"tool_use": {"name", "input"}}` is one
  tool_use reply (give it the id `toolu_<call index, 3 digits>`; ids never reach `expect`).
- `expect.output`: the pattern's result (shapes below).
- `expect: {"error": true}` instead of `output`/`calls`: the run must fail with an error. Assert only that an error occurs, never its text. A runner that
  fails because the script ran out of replies has not passed: an error case must fail by validation, not by asking for more replies than scripted.
- `expect.calls`: every model call in order as `{"agent", "role"}`. Tool calls are not listed.
  A tool's `is_error` is the tools' own flag. The contract pins it only for an unknown tool name (`is_error: true`) and for the real read tools
  on a valid call (`false`); a runner's tool stub must do the same. Tool output text never reaches `expect`.

## Running a case

Run the pattern with a fake model that returns `scripted[i]` for the i-th call (an extra or missing call is a failure),
the ticket, and, for `parallel`, **one worker** (the fan-out runs in slot order so call order is fixed). The tools are
the real lumen-read MCP tools (`get_ticket`, `search_tickets`), one session per ticket, called one at a time.

| pattern | `output` | `calls` (agent, role) |
|---|---|---|
| chain | `{category, reply}` | classifier/classify, writer/reply |
| route | `{route, reply}` | router/route, `<route>`/reply |
| parallel | `{lookups: [{tool, args, is_error}], summary}` | lookup-1..3/lookup (slot order), summarizer/summarize |
| orchestrate | `{plan: [str], results: [str], reply}` | orchestrator/plan, worker-N/work (once per model call, tool rounds included), synthesizer/synthesize |
| evaluate_optimize | `{rounds: [{draft, verdict: {addresses_issue, tone, no_false_promises: bool}}], final}` | writer/draft, judge/judge, then writer/revise + judge/judge per extra round |

## Comparing

- Deep equality on **parsed JSON**: key order and whitespace do not matter; array order does.
- Strings compare exactly, code point for code point. There are no floats in this file; integers (such as `limit`) compare exactly.
- Validation failures are cases with `expect: {"error": true}` (Python raises `ValueError`; Go returns an error): a route outside billing, bug,
  account, other; a category outside the lab's six; a plan that is empty, longer than 3, or holds a non-string; a judge reply that is not JSON or lacks
  a boolean `pass` for each rubric id; a lookup reply without a tool call.
- **Parsing model JSON.** Parse from the first `{` or `[` in the reply (whichever comes first); text before it is ignored, and so is text after the first
  complete JSON value. No brace or bracket at all is an error.
- **Whitespace and case (R22).** A reply's text is trimmed of ASCII whitespace only (space, `\t`, `\n`, `\r`), so a no-break space is not trimmed. A route is
  also lowercased for A-Z only, never other letters. Go's `strings.Trim(s, " \t\n\r")` and an A-Z lowercase match this exactly; `str.strip()` and
  `str.lower()` (Unicode-aware) do not, so Python uses the explicit ASCII rule too.
- `evaluate_optimize` stops on the first round whose three verdicts pass, and after 3 rounds otherwise (`final` is then the last draft).

## Desks: `single` and `supervisor`

`pattern` is `single` (the single agent) or `supervisor`: one case per desk per sample ticket, then extra cases (a
handoff to an unknown worker, a non-string task, a bad triage answer, a review with no draft, a bad review reply, a new
draft that resets the review, and both turn caps at `MAX_TURNS = 8`). Run them on lumen-read **and** lumen-ops, one
session per ticket, with the person and the server both saying yes (Python: `approve="accept"`, `elicit="accept"`, a
temporary labels file). So a `label_ticket` that reaches the tools succeeds (`is_error: false`) and writes one row; one
the desk refuses never reaches them (`is_error: true`). A runner's stub must answer `label_ticket` as a success here
(and still as an unknown tool in the pattern cases, where lumen-ops is not open).

| desk | `output` | `calls` (agent, role, tools) |
|---|---|---|
| single | `{reply, stop, tool_calls, errors}` | single/act, every call offered all four tools |
| supervisor | `{reply, stop, tool_calls, errors, handoffs, state}` | supervisor/supervise, triage/triage, research/research, drafter/draft, reviewer/review |

- A desk `calls` entry also holds `tools`: the tool names offered to that call, sorted (`[]` for none). This is where
  the contract pins the gate: research is offered the three lumen-read tools only, triage/drafter/reviewer none, and
  the supervisor `["handoff"]` until the reviewer has passed the current draft, then `["handoff", "label_ticket"]`.
- `stop`: `end_turn` (a reply with no tool call) or `max_turns` (then `reply` is `[stopped: reached MAX_TURNS without finishing]`).
- `tool_calls`: every MCP tool call (a lumen-read or lumen-ops name), in order, as `{agent, tool, args, is_error}`;
  handoffs are not listed. A desk tool the caller was not offered is refused by the desk (`is_error: true`) and never
  reaches the tools: `label_ticket` from research, from the supervisor before the review passed (or in the same
  response as the reviewer's handoff), and a supervisor `label_ticket` whose `id` is not the ticket's or whose `label`
  is not the triaged `state.category` (R27).
- `errors` (R35/R37, the same rule in every engine): a call whose name is neither a desk MCP tool nor a known worker,
  as `{agent, tool, args, result}`, in order. In the hand-built desks that is a made-up tool name (`write_file`:
  `tool` is that name, `result` is `"Unknown tool: <name>"`) or a handoff to an unknown worker (`billing-bot`: `tool`
  is `"handoff"`, `args` the handoff's input, `result` is `"Unknown worker: <worker>. Workers: triage, research,
  drafter, reviewer"`, a non-string worker written as JSON, e.g. `null`). Such a call never reaches the tools, is
  never in `tool_calls` or `handoffs`, and leaves no handoff Trace record; the model gets `result` as an error tool
  result and the loop goes on with the state unchanged (R26). `result` is the desk's own text, so the contract pins
  it. The LangGraph engine (not in the contract) fills `result` with LangGraph's own error text and `tool` with the
  name the model called (a worker tool there, e.g. `billing-bot`). The Agent SDK engine (not in the contract) logs
  `tool: "Agent"` with the Agent call's input as `args` for an unknown worker (`subagent_type` such as `billing-bot`
  or the CLI's `fork`), or the name called for any other tool, and `result` is the CLI's error text (e.g.
  `"PreToolUse:Agent hook error: Unknown worker: billing-bot. Workers: ..."`).
- `handoffs`: `{worker, task, is_error, changed}` with `worker` and `task` exactly as the model sent them (a known
  worker only). `changed` is the state diff: only the fields whose value changed. A failed handoff (non-string task, a worker
  answer that fails validation, a review with no draft) is `is_error: true` with `changed: {}`, and the supervisor reads
  the error and carries on: a bad tool call is information for the model, as in the harness, not a crash.
- `state`: `{ticket_id, category, findings, draft, review}`, a field not yet set is `null`; `review` is
  `{passed, verdict: {addresses_issue, tone, no_false_promises}}`. A new draft sets `review` back to `null`, and so
  does a triage that changes `category` (R30); a re-triage to the same category leaves it.
- The supervisor's `reply` is the reviewed draft when `review.passed` is true, else its own last text (at the cap:
  the `max_turns` reply above).
- Every cap leaves a Trace record `{kind: "stop", name: "max_turns" | "max_worker_steps"}` (R29), agent `single`,
  `supervisor` or `research`; not in `expect`.
- Reviewer reasons (in the result text only): a string as is, null or missing as `""`, anything else as JSON.
- The Trace's handoff records (Python `kind: "handoff"`) are not in `expect`; their name is `"<worker>: <changed fields,
  sorted, comma-separated>"`, `"<worker>: no change"` or `"<worker>: error"` (a known worker's failed handoff).
