# Shared contract: `contract.jsonl`

Both Lumen servers (Python and Go) must pass every case for their `server` value. The file is generated by
`.venv-mcp/bin/python mcp/fixtures/gen_contract.py` (`--check` fails if the file is stale); expectations come from `lumen_core`
and hand-typed error texts, not from a server. Edit the generator, never the JSONL.

## Line format

`{"name", "server": "read"|"ops", "method", "params", "expect"}` (ops cases add `answer`, below), one JSON object per line, ASCII-escaped
(a literal nbsp, İ or Σ appears as `\u00a0`, `\u0130`, `\u03a3`; parse the line as JSON and you get the real character).

## Running a case

| method | params | how to run it |
|---|---|---|
| `tools/call` | `{name, arguments}` | call the tool |
| `resources/read` | `{uri}` | read the resource |
| `prompts/get` | `{name, arguments}` | get the prompt |

## `expect` shapes (what to turn the response into before comparing)

- **tools/call**
  - success: `{"structured": <structuredContent>}`.
  - `isError` true: `{"error": <content[0].text>}`. The text must be exactly the fixed message (no prefix), and there is no structuredContent.
- **resources/read**
  - success: `{"contents": [{"uri", "mimeType", "json"}]}` where `json` is the entry's `text` parsed as JSON.
  - failure: `{"error": <JSON-RPC error message>, "code": <JSON-RPC error code>}`. The message is the fixed text (`unknown ticket: {id}`) and the code is -32602 (INVALID_PARAMS), in both servers.
- **prompts/get**
  - success: `{"contents": [{"role", "text"}]}`, one per message (text content).
  - failure: `{"error": <JSON-RPC error message>, "code": <JSON-RPC error code>}`, as for resources (-32602).

## Ops cases (`server: "ops"`, lumen-ops `label_ticket`)

An ops case writes, so each one runs on a **fresh server** with a **fresh, empty labels file** (a temp path,
never `mcp/data/labels.jsonl`). The case carries one more field:

- `answer`: what the test client's elicitation handler replies if the server asks for confirmation:
  `{"action": "accept", "content": {"confirm": true}}`, `{"action": "decline"}`, `{"action": "cancel"}`, ...
  `null` means the server must not ask; if it does anyway, the handler records the question and declines,
  and the recorded `asked` then fails the compare.

Let the SDK client drive the rounds (Python `Client(..., elicitation_callback=...)`, Go
`ClientOptions.ElicitationHandler`). Turn the outcome into the tools/call shape above (`structured` or `error`),
plus two keys:

- `asked`: the elicitation the handler was shown, `{"message", "requestedSchema"}`, or `null` if it was never
  called. At most one question per case. Both servers send exactly
  `Set ticket {id} to "{label}"?` and `{"type": "object", "properties": {"confirm": {"type": "boolean",
  "title": "Confirm"}}, "required": ["confirm"]}`.
- `rows`: every row in the labels file after the call, in file order, each **without its `time` key** (the one
  field a contract cannot pin; tests check it separately). In-process there is no auth, so `client_id` is
  `"anonymous"`.

Replayed, forged and expired request states are not contract cases: the two SDKs answer them differently
(Python: JSON-RPC error; Go: the fixed decline), so each language's own tests assert "no row written".

## Comparing

- Deep equality on **parsed JSON**: object key order and whitespace do not matter; array order does.
- Numbers: floats compare with an **absolute tolerance of 1e-9** (ruling R16, the same as the Task 3 parity rule); integers and everything else exactly. `true` is not `1`. `1` and `1.0` compare equal (both are the number one once parsed).
- `results` is always an array: `[]` when nothing matches, **never `null`** (so Go must initialise the slice).
- Strings compare exactly, code point for code point. Lengths in the limits are counted in **characters (code points)**, not bytes.
- Search uses ASCII-only rules: lowercase A-Z only, split on space, `\t`, `\n`, `\r`, `\v`, `\f` only. `\x1f` and nbsp do not split; `İ` and `Σ` are not case-folded.

## Fixed error texts

`query must be 1 to 200 characters`, `limit must be 1 to 20`, `text must be 1 to 20000 characters`,
`unknown ticket: {id}` (also for the resource, and for the prompt when the id is not `t` plus three digits or not a known ticket),
`label must be one of: billing, bug, account, how_to, feature_request, outage`, `label not written: the user declined`.
`label_ticket` checks the label first, then the ticket, and asks nothing when either is wrong.

## Known difference: the labelling App (Python only)

`lumen-ops` in Python serves the labelling MCP App: a `ui://lumen/label.html` resource (mime
`text/html;profile=mcp-app`) and `_meta.ui.resourceUri` on `label_ticket`'s `tools/list` entry. Go does not
(spec and ruling R6: the App is Python-only), so `tools/list` and `resources/list` differ between the two
`lumen-ops` servers by that App-only metadata. The contract cases only call tools and read resources and never
compare `tools/list` or `_meta`, so they are unaffected; `label_ticket`'s inputs, outputs, errors and elicitation
are identical in both languages.
